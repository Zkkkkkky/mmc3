# ROM 定制修改器建设方案（可复用方法论）

> 文档定位：把“新 DC 修改器”项目中已经验证有效的工程方法沉淀为后续 ROM 定制修改器的建设蓝本。本文描述通用流程、分层和质量门禁；《第二次机器人大战》的 Mapper、Bank、偏移、记录长度和参考 EXE 行为仍以本仓库专属文档为准，禁止直接套到其他 ROM。
>
> 适用范围：优先面向 FC/NES 二进制 ROM；用于其他主机时，可以保留证据、事务、测试和交付方法，但必须替换文件头、地址映射、Bank/分页、图形、音频和模拟器适配层。

## 1. 建设目标

一个可交付的定制修改器不只是“把几个地址做成输入框”，而应同时具备：

1. **识别正确 ROM**：拒绝未知版本、错误 Mapper、错误容量和关键代码签名不匹配的输入。
2. **无损读取与写回**：未修改内容保持原字节；已修改内容能追溯到语义操作和 ROM 偏移。
3. **安全编辑**：越界、超容、悬空指针、资源重叠、非法操作码和部分写入在落盘前被拒绝。
4. **证据驱动**：每个开放写入的字段都有静态或动态证据；不确定内容先只读，不靠猜测写 ROM。
5. **可验证交付**：提供自动测试、模拟器运行证据、人工验收清单、构建报告和 SHA-256。
6. **可扩展但不互相污染**：游戏专属布局放在 Profile/Codec 中，通用工程、事务、校验、打包能力可以复用。

本方案的核心结论是：

> **先建立 ROM 身份与证据链，再做 Codec；先证明字节闭环，再做界面；先保护未知区域，再考虑扩容和引擎改写。**

## 2. 已验证的工程原则

### 2.1 具体地址不可复用，方法可以复用

可跨项目复用的是 ROM 映像、地址换算、变更集、资源图、原子保存、IPS、验证报告、黄金对照框架和打包流程。以下内容必须针对每个 ROM 重新取证：

- 文件哈希、容量、Mapper/映射模式和 Bank 大小；
- 指针表、记录结构、文本编码、压缩格式、CHR/调色板布局；
- 空闲区、受保护区、镜像字段、保存归一化副作用；
- 运行时 RAM、跨 Bank 调用、脚本操作码和引擎补丁；
- 参考修改器的控件、保存模型和真实落盘行为。

### 2.2 “已实现”和“已证明”是两个状态

界面可操作、测试能跑、甚至 ROM 能启动，都不等于字段已经对齐。建议统一使用以下状态：

| 状态 | 含义 |
|---|---|
| 未实现 | 尚无读取或编辑能力 |
| 只读/禁用 | 能识别或展示，但没有安全写入依据 |
| 已实现（未验证） | 已有写入实现，但缺黄金差分或运行时证据 |
| 部分实现 | 仅安全子范围开放，仍有明确禁区 |
| 已验证 | 字节闭环、保存重开和相关运行时验证已通过 |
| 超集能力 | 参考工具没有、由新产品提供的工程或安全增强 |

状态升级必须由证据触发，不能由开发进度描述替代。

### 2.3 输入、工作副本和输出严格分离

- `references/`：不可变的基准 ROM、参考工具、资料、音频和模拟器状态。
- 内存工作副本：所有语义编辑和撤销/重做只作用于工作副本。
- `output/`：派生 ROM、IPS、报告、映射、验证证据和发布程序。
- 默认不覆盖用户的基准 ROM；如产品决定支持原地保存，也应采用临时文件加原子替换，并保留明确的风险策略。

### 2.4 未知字段默认不写

“看起来像空白”“地址附近都是 00/FF”“参考工具有按钮”都不是安全依据。未知内容只能：

- 只读展示；
- 记录为待验证；
- 在隔离副本上做探针；
- 得到可重复证据后再逐项解禁。

## 3. 推荐分层架构

```text
GUI / 命令行
    │ 只传递语义值，不直接计算文件偏移
应用与会话层
    │ 草稿、确定/取消、撤销/重做、工程文件、构建
领域模型与 Codec
    │ 记录、文本、地图、脚本、图形、音乐的无损编解码
ROM Profile + RomImage
    │ 身份识别、地址换算、Bank 边界、受保护/可用区域
原始字节

横向能力：ChangeSet｜ResourceGraph｜Validation｜Golden Pipeline｜Reports
```

| 层 | 职责 | 禁止事项 |
|---|---|---|
| ROM 映像层 | 校验文件头、容量、平台/Mapper、哈希和地址范围；提供文件偏移与 CPU/Bank 地址换算 | 不承载具体界面逻辑 |
| Profile 层 | 描述某个 ROM 版本的身份、表地址、数量、窗口基址、容量、保护区和功能开关 | 不在业务代码散落硬编码偏移 |
| Codec 层 | 字节与领域对象双向转换，保留未知位和原始 Token | 不直接弹窗，不静默改写无关字节 |
| 领域/服务层 | 引用关系、资源分配、容量、事务、全局一致性校验 | 不绕过 Profile 和 Codec 写字节 |
| 应用会话层 | 草稿、提交、撤销/重做、工程重放、构建 ROM/IPS/报告 | 不把控件状态当作唯一数据源 |
| GUI 层 | 导航、编辑、预览、错误反馈和人工验收动线 | 不直接打开 ROM 后按固定偏移写入 |
| 工具与证据层 | 反汇编、探针、黄金差分、报告、截图、模拟器冒烟 | 不把研究脚本当作发布产品入口 |

当前仓库中可作为实现参考的对应关系：

| 能力 | 当前实现位置 | 后续项目建议 |
|---|---|---|
| ROM 身份与边界 | `src/fc_editor/rom_image.py`、`profiles.py` | 提取接口，重新编写目标游戏 Profile |
| 无损编解码 | `src/fc_editor/codecs/` | 保留 Codec 约定，按资源逐个重写 |
| 可逆变更 | `src/fc_editor/changes.py` | 可直接复用思想和大部分实现 |
| 资源图与分配 | `src/fc_editor/resources.py` | 仅在空闲区和引用语义已证明后启用 |
| 会话与构建 | `src/fc_rom_editor_core.py`、`project.py` | 抽离游戏专属分支后复用 |
| 全局校验 | `src/fc_editor/services/validation.py` | 改成规则注册表，按 Profile 组合 |
| GUI 壳 | `src/dc_modifier/` | 复用交互范式，不复用游戏字段和文案 |
| 黄金对照 | `tools/golden_pipeline*.py` | 复用档案与统计协议，替换参考工具驱动 |

## 4. 新项目目录与产物边界

建议继续采用本仓库已经验证的目录纪律：

| 目录 | 内容 |
|---|---|
| `src/<game>_modifier/` | 目标游戏 GUI 与应用组合 |
| `src/rom_editor/` | 可复用 ROM、事务、资源和校验核心 |
| `src/<game>_editor/codecs/` | 目标游戏专属 Codec |
| `src/resources/default_config/` | 默认码表、字段定义和只读配置 |
| `src/asm/` | 必须进入 ROM 的汇编补丁源码 |
| `tools/research/` | 逆向探针、批量采集和一次性研究脚本 |
| `tools/` | 构建、报告、打包、清单和验证脚本 |
| `tests/` | 唯一自动测试发现根 |
| `tests/emulator/` | 模拟器脚本和运行时断言 |
| `docs/` | 需求、数据字典、设计、使用说明、验收与开发记录 |
| `references/` | 只读输入，绝不作为构建输出目录 |
| `output/` | ROM、补丁、应用、报告、证据、映射和中间产物 |

每次正式交付至少包含：

- 发布程序或启动方式；
- 用户提供基准 ROM 后可生成的派生 ROM/IPS；
- 构建报告与 SHA-256；
- 地址/字段映射表；
- 已验证能力和明确限制；
- 自动测试结果、模拟器结果和人工验收入口；
- 不包含无授权商业 ROM 的公开分发包。

## 5. ROM Profile 契约

Profile 是支持新 ROM 的第一份可执行规格。建议至少声明：

```text
identity
  platform / header format / mapper or memory map
  exact size / known SHA-256 / variant key
addressing
  header and trainer size
  PRG/CHR bank size
  CPU windows and bank-to-file conversion
resources
  pointer tables / record counts / data ranges
  text, map, graphics, audio and script specs
safety
  protected ranges / proven free ranges
  required code signatures / mirrored bytes
  normalization or checksum rules
capabilities
  read-only / fixed-write / repack / relocation / runtime-patch
```

### 5.1 身份识别顺序

1. 校验文件头和声明容量；
2. 校验平台、Mapper 或映射模式；
3. 匹配精确 SHA-256；
4. 对允许的派生版本校验关键代码签名、保护区哈希和布局描述符；
5. 无法唯一归类时拒绝写入，可提供只读十六进制查看。

不能只按文件名、大小或单一地址的“魔数”识别 ROM。

### 5.2 多版本兼容策略

| 级别 | 条件 | 权限 |
|---|---|---|
| 精确基准 | 完整哈希命中 | 可执行该 Profile 已验证的全部能力 |
| 已登记派生 | 布局描述符、关键签名和保护区哈希命中 | 仅开放明确兼容的能力 |
| 同游戏未知版本 | 头部/Mapper 相似但身份不明 | 默认只读，禁止工程重放 |
| 不兼容 | 容量、映射或签名冲突 | 拒绝载入 |

每个 Profile 必须有独立测试夹具；不要让“支持多个版本”退化为大量散落的条件分支。

## 6. 数据类型与风险分级

先给资源分类，再决定实现方式和验证门槛：

| 等级 | 典型资源 | 写入策略 | 解禁条件 |
|---|---|---|---|
| R0 | 未知字段、运行时易失值、无效按钮 | 只读/禁用 | 新证据改变分类 |
| R1 | 固定偏移标量、位域、定长记录字段 | 原位写入，保留未修改位 | 单字段差分、重开、边界值 |
| R2 | 指针表、共享记录、定长文本/图块 | 更新目标和必要引用，禁止隐式拆分 | 引用计数、别名、相邻隔离、往返 |
| R3 | 变长文本池、压缩地图、脚本池、CHR/音频资源 | 全池重建或受控重定位 | 容量、指针图、确定性重建、超容零写入 |
| R4 | Mapper 扩容、解释器、跨 Bank 调用、RAM/音频引擎补丁 | 汇编补丁和运行时验证 | 静态签名、汇编断言、模拟器轨迹、回退方案 |

风险等级不是开发优先级。建议先完成一个 R1 垂直切片，再逐步进入 R2/R3；R4 单独立项，不与普通字段编辑混在一次交付中。

### 6.1 Codec 的最低要求

每个 Codec 都应满足：

- `decode(original_bytes) -> model`；
- `encode(model, original_bytes) -> bytes/patches`；
- 未知位、保留字节、原始 Token 和别名默认保留；
- 输入非法时在生成补丁前失败；
- 无修改往返必须字节一致；
- 修改一个字段时，变化范围可预测并可审计；
- 变长资源必须返回容量、引用更新和冲突信息。

压缩数据分区的“当前正文结束位置”不能直接当成容量上限。容量边界必须来自已验证的可写物理边界（例如当前映射 Bank 的末尾）、参考工具保存差分及引用审计；否则会把正文后的可用尾部误报为已占满。反过来，也不能只因尾部是零或参考工具曾写入就假定整段安全，仍须确认没有其他资源或运行时入口引用。状态提示应分别显示当前占用和验证容量，并以验证容量执行重排、保存重开及超限零写入测试。

若运行时用可写分界值而非固定 ID 决定记录属于哪个 Bank，Codec 必须把分界字节视为资源元数据，而不能把初始分组固化在 Profile 中。变长保存应先解码全部记录，再按编号和每 Bank 的真实起始地址/末尾执行确定性贪心分配；提交时把分界、完整指针表和所有受影响 Bank 正文作为一个原子事务更新。测试至少覆盖一次级联迁移：前一 Bank 溢出导致末项移入下一 Bank、下一 Bank 再把末项移入第三 Bank，并验证全部记录语义、运行时分界、工程重放、ROM 重开和撤销。

优先让 Codec 生成补丁或完整候选副本，再由事务层统一应用；不要让多个界面组件各自写同一片 ROM。

## 7. 逆向与证据体系

### 7.1 先建立证据账本

新项目启动时应先确定证据类型、可信顺序和冲突裁决规则。参考修改器存在时，可采集控件树、截图、操作录屏和真实保存差分；没有参考修改器时，以静态反汇编、调试器读写断点、模拟器轨迹和可重复 ROM 实验替代。

界面上看似属于某条记录的属性，必须先确认运行时是否真的从该记录读取。若代码对地图格、对象编号或状态位使用全局立即数判断，编辑器应把它建模为全局字段，并在所有相关对象中同步显示；不能为了表格观感伪造为每条记录各自独立。对于可编辑的运行时立即数，应同时校验前后机器码签名、操作数范围、共享分支和计算链。例如多个效果汇入同一乘除入口时，比例控件必须明确说明会共同受影响；若要拆分语义，则属于新增运行时 Hook，必须另行完成空间、寄存器、Bank 映射和模拟器验证，不能只改界面标签。

每条结论至少记录：

- 资源/字段稳定 ID；
- 当前结论和状态；
- ROM 版本及 SHA-256；
- 证据类型、文件路径、采集时间；
- 文件偏移、Bank/CPU 地址及换算规则；
- 请求值、原值、写后值和重开值；
- 已知副作用、别名、镜像和未决问题。

本项目的 E1—E5 是针对“有参考 EXE”场景建立的项目内分级，不应原样套给所有游戏。新项目应在需求阶段固定自己的分级，并明确“运行时字节证据、静态代码证据、参考 UI 证据、人工资料、当前产品行为”发生冲突时谁优先。

### 7.2 推荐的取证顺序

1. 记录 ROM 身份、头部、容量和初步 Bank 图；
2. 通过已知文本、数值或图块定位候选表；
3. 改一处、对比一处，确认步长、端序、位域和索引基数；
4. 用首项、普通项、末项和边界值验证数量与跨度；
5. 检查指针引用、别名、镜像和保存副作用；
6. 静态追踪读取/写入代码，确认运行时解释；
7. 在模拟器中用读写断点或 Lua 验证真实消费路径；
8. 把结论写入 Profile、数据字典和自动测试，而不是只留在聊天或临时笔记里。

### 7.3 参考修改器的黄金对照

存在旧修改器或官方工具时，对每个可写字段执行四步闭环：

1. 从同一基准复制 `before` 和 `after`；
2. 在参考工具中只修改一个字段并完成其真实保存动线；
3. 对两份文件做全字节差分，剔除已证明的保存归一化；
4. 关闭参考工具，以全新进程重开 `after` 并读取同一字段。

混合修改只能用于综合回归，不能证明单字段映射。失败、超时、零写入和不可达控件也要存档，它们可能构成否定证据。旧式 Win32 窗口的 Label ID 与 Edit ID 未必连续或按视觉顺序分配；单字段保存差分只能证明“编辑框→ROM 偏移”，还必须使用控件树矩形坐标把标签与其正下方/右侧的编辑框配对，并以窗口截图的显示值交叉检查。禁止仅凭控件编号相近程度推断字段语义。

## 8. 黄金档案与字段注册表

建议每个字段使用稳定 ID，例如：

```text
M05/unit/003/hp
M06/character/012/spirit/04/cost
M14/chapter/07/action/015/operand/02
```

字段注册表至少包含：

| 字段 | 说明 |
|---|---|
| `field_id` | 稳定、不可随界面文案变化的逻辑 ID |
| `module` / `record_id` | 模块与记录身份 |
| `status` | writable / read_only / no_effect / unsafe 等 |
| `expected_offsets` | 必写偏移或偏移生成规则 |
| `optional_offsets` | 仅特定进位、压缩或镜像条件下变化的偏移 |
| `normalization` | 已证明且应从参考差分剔除的副作用 |
| `source_case` | 一手证据路径与 SHA-256 |
| `reopen_mode` | 同进程或全新进程，正式对齐应优先全新进程 |
| `risk_level` | R0—R4 |

每个黄金用例至少保留：

- before/after 哈希；
- 请求值与重开值；
- 完整变化偏移和前后字节；
- 必写、可选、已剔除和未知偏移；
- 参考程序首进程/重开进程身份；
- 耗时、结果和错误信息；
- 用例配方版本及来源证据哈希。

覆盖率必须按“唯一逻辑字段”计算。控件出现次数、截图数量、采集场景数、指针别名数或临时登记数量都不能冒充字段分母。

## 9. 事务、保存与写入安全

### 9.1 两级或三级提交

推荐保存模型：

1. **控件草稿**：用户输入尚未影响项目；
2. **项目提交**：点击确定或应用后形成语义操作/ChangeSet，可撤销；
3. **文件落盘**：显式保存或构建时，统一校验并原子写出派生 ROM。

取消必须丢弃草稿；验证失败必须整体拒绝；任何异常都不能留下半写文件。

同一窗口用页签或切换按钮编辑多条同构记录时，每条记录都应有独立草稿；切换只能暂存控件值，不能提前写入项目。最终应用前统一传播真正的全局字段，再把所有有变化的记录放进一个外层事务，使一次“应用”只产生一条撤销记录。测试至少覆盖“记录甲修改→切到记录乙修改→切回甲仍保留→一次应用→一次撤销全部恢复”，并验证取消窗口对所有记录均为零写入。

### 9.2 ChangeSet 要求

每个补丁操作应记录：

- 起始偏移和长度；
- 修改前字节、修改后字节；
- 来源模块和语义描述；
- 可选的预期前像；
- 与其他操作是否允许重叠。

应用补丁前校验前像可以防止把旧工程重放到不匹配 ROM。不同来源的写入发生重叠时默认报错，而不是以后写覆盖先写。

### 9.3 面向初学者的任务向导

完整 ROM 修改器不应要求用户先理解 Bank、指针、偏移或内部模块名。推荐提供随时可打开的任务向导，并遵循以下规则：

- 用“修改人物头像”“调整关卡部署”“最终检查与导出”等目标组织入口，而不是按地址表或 Codec 名称组织；
- 每个任务只给出可执行的短步骤、完成后结果和一个最重要的风险提示，并能直接跳到目标页面；
- 显式解释“控件草稿 → 页面暂存/应用 → 窗口确定 → 文件落盘”的状态边界，避免用户把预览、暂存或关闭窗口误认为已保存；
- 前置条件不足时禁用跳转并说明下一步，例如先打开 ROM，而不是让用户进入空白窗口；
- 高频核心字段应优先组成无需滚动的首屏工作区，并尽量沿用用户熟悉的参考工具分区；技术地址、原始字节和长篇安全说明折叠保留，不能用永久占位的大段文字挤走主要操作；全局页签、分组框、按钮和输入框使用一致的紧凑间距，但不得缩小点击目标到难以操作；
- 容量已满或证据不足的入口应可查看原因和替代路径，不能只显示无解释的灰按钮，也不能为了可点击而猜测写入协议；
- 向导只改善发现性和操作顺序，不提升字段证据等级；所有写入仍经过同一 ChangeSet、容量和构建门禁。

### 9.4 全局构建校验

落盘前至少检查：

- Profile 身份仍匹配；
- 所有写入在 ROM 边界内；
- 受保护区域未被意外修改；
- 指针落在允许窗口且目标完整；
- 定长记录数量、跨度和保留位正确；
- 变长池不超容量、不重叠、不产生悬空引用；
- 压缩资源可重新解码；
- 脚本能到达合法结束码，跳转目标位于有效指令边界；
- 图形、文本、音频格式满足目标引擎约束；
- 校验和、镜像或布局描述符同步更新；
- 输出重新载入后能得到期望模型。

构建流程应先在内存中生成完整候选 ROM，校验通过后再写临时文件并原子替换目标。生成 IPS 时还应做一次“基准 + IPS = 输出 ROM”的反向验证。

### 9.5 资源图和空闲区

只有同时满足下列条件，某段空间才可标记为可分配：

1. 静态扫描没有指针或代码引用；
2. 运行时关键路径没有读取；
3. 多份相关 ROM 中用途一致；
4. 区域内容符合预期空闲模式；
5. 经过模拟器回归；
6. Profile 明确声明范围、Bank 边界和对齐。

资源分配器应确定性运行：相同输入和工程操作必须生成相同布局与哈希。资源使用稳定 ID，不以界面显示名或随机顺序定位。

### 9.6 缺字分配与字库整理

文字编辑器不能把“Unicode 可输入”误当作“ROM 已有编码”。提交字段前应先用工程码表解析全文，对缺字执行确定性的安全槽分配，再把字模、Token→Unicode 工程映射和原字段正文放入同一外层事务；任一步失败都必须零写入。字库页可达性是显示例程的属性，不能仅配置“优先级”后把其他页当作兜底：每个文字通道必须声明允许页集合，编码表也必须过滤到该集合。当前基线的剧情/战斗允许 B/C/D 十二页；人物、机体、武器、道具和系统资料名称保守限定为 C8—CB/D8—DB。若同一 Unicode 字符先在剧情专用 B 页分配、之后用于名称，应新增一份 C/D 页兼容别名，而不是让名称继续引用 B 页，也不应搬移仍被剧情引用的原 Token。

未使用检测必须排除字模物理存储区，避免点阵数据自身形成伪引用。正引用结果采取保守策略：出现过的 Token 一律保留。工程自定义映射只有在当前零引用时才允许同步清空固定字模和移除映射。内置码表文字采用更严格的可逆回收：必须属于独立 18 字节字模、扫描为零引用，提交瞬间再次复核；通过后清空字模并写入工程级 `font.disable_builtin` 元数据，从有效码表排除该 Token，使其成为可重分配槽。整批回收属于一个撤销事务，并可从不可变基准 ROM 恢复尚未重新分配的字模；已经建立新映射的槽禁止恢复覆盖。原有安全空槽始终以不可变基准 ROM 判定，工作副本清空产生的新字节组合不得扩大候选集；每次实际分配还须重新检查当前工作 ROM 引用与字模状态，防止基准安全槽在其他编辑中被写入原始 Token 后仍遭复用。无映射遗留图形因无法证明文字身份，继续只报告。

### 9.7 固定边界的隐藏文字块

不在常规指针表中的制作名单、彩蛋或固定界面文字，不能仅凭“看起来像字符串”整体开放。应先区分不可编辑的绘图/控制前缀、可见文字载荷、独立结束码和紧邻后续数据，以确定固定写入边界。编辑器只暴露可见载荷，将运行时分行/对齐控制码投影为换行和空格；提交时恢复原控制码，较短内容用已验证的原填充码补齐，超长内容原子拒绝，不移动后续数据。

同一 Unicode 字符可能有重复 Token，解码后再按全局首选编码会造成无关字节变化。固定文字编辑必须对未改片段使用“保留原 Token”的编码策略，只让真正修改的文本选择新编码；缺字分配、正文和字模仍置于同一事务。验收至少覆盖同文零差分、缩短后边界外零变化、超容零写入、撤销/重做和保存重开，并把运行时可达性与静态结构安全分开陈述。

固定文字的物理载荷独立，不等于它在产品信息架构中应成为独立模块。若调用链证明文字由某个动画或事件脚本绘制，底层仍可保留专用 Codec，但入口应内嵌到调用它的上层编辑器，并与上层草稿统一确定、取消和撤销。除字节容量外，还须从原版面冻结最大行数和单行显示格；只满足字节上限、却增加行数或越过屏幕宽度的内容必须拒绝。制作信息/出演名单即采用此模型：Bank `$3D` 文字载荷由地图动画 `$13/$14` 驱动，动画窗口暂存文字，最终外层事务统一提交。

## 10. 推荐实施路线

### 阶段 0：立项与冻结输入

交付：

- 项目目标、范围和不做事项；
- 合法的用户自备 ROM 使用方式；
- 基准 ROM 身份表；
- `references/` 只读约束；
- 证据分级、目录规范和开发记录模板。

退出条件：任何成员都能回答“支持哪份 ROM、输出到哪里、哪些输入不可修改”。

### 阶段 1：ROM Profile 与只读浏览

交付：

- 文件头/Mapper/容量校验；
- Bank 地址换算；
- 初始资源图；
- 一个或多个 Profile；
- 十六进制和结构化只读查看；
- 基准哈希及关键签名测试。

退出条件：错误 ROM 被稳定拒绝，正确 ROM 的关键表能无损读取。

### 阶段 2：第一个 R1 垂直切片

选择一个固定字段，从数据字典一路做到：

```text
证据 → Profile → Codec → ChangeSet → 校验 → UI → 保存 → 重开 → 模拟器
```

退出条件：单字段黄金差分无未知偏移，取消/撤销/保存重开均通过。这个切片将成为后续模块模板。

### 阶段 3：按资源族扩展

推荐顺序：

1. 固定标量和定长记录；
2. 位域、枚举和记录间引用；
3. 文本、图形和压缩地图；
4. 共享池、指针表和重打包；
5. 脚本、动画、音频；
6. 扩容和运行时引擎补丁。

每个模块都采用同一闭环：取证 → 数据字典 → Codec → 安全门禁 → UI → 自动测试 → 模拟器 → 用户验收。

### 阶段 4：工程与高级能力

在基础写入稳定后增加：

- 工程文件与语义操作重放；
- 撤销/重做；
- 资源占用图和确定性分配；
- 导入/导出包；
- IPS、差分报告和映射表；
- 多 Profile 兼容。

工程文件应保存基准身份、操作版本和原始前像。格式升级需要迁移版本，不能悄悄改变旧工程语义。

### 阶段 5：产品化交付

交付：

- 离线可运行的 GUI/CLI；
- 使用说明和限制；
- 自动测试、运行时证据和人工验收清单；
- EXE/包、校验和、文件清单；
- 可从干净环境重复执行的构建命令。

退出条件：交付件能够仅凭文档从基准 ROM 重建，且产物哈希、报告和已知限制可追溯。

## 11. 测试与验收体系

### 11.1 自动测试分层

| 层级 | 关键断言 |
|---|---|
| Profile/地址测试 | 已知 Bank/CPU/文件偏移互相换算；越界和错误版本被拒绝 |
| Codec 单元测试 | 无修改往返一致；边界值；保留位；非法输入 |
| 字节黄金测试 | 单字段只改变允许偏移；已知镜像和副作用显式列出 |
| 资源测试 | 指针、别名、压缩、容量、重排、确定性和超容零写入 |
| 事务测试 | 确定/取消、撤销/重做、前像冲突、跨模块重叠 |
| 工程测试 | 保存/加载/迁移/重放得到同一产物 |
| UI 测试 | 控件状态、草稿隔离、错误反馈和关键动线 |
| 构建测试 | ROM/IPS/报告一致，输出可重新载入 |
| 打包测试 | 发布程序离线启动、自检、打开推荐输入 |

必须加入以下反例：

- 错误 ROM、截断 ROM、错误头部和不支持版本；
- 最小值、最大值、首记录、末记录；
- 满池、差一字节超容、跨 Bank、未对齐；
- 悬空指针、循环引用、共享记录拆分；
- 非法 Token/操作码、缺少结束码；
- 取消后零变化、失败后零变化；
- 撤销后与从未修改完全一致；
- 同一工程连续构建两次哈希一致。

### 11.2 模拟器验证

静态字节正确不代表游戏会正确消费。以下改动必须做模拟器验证：

- 运行时脚本、战斗公式、地图事件和 AI；
- Mapper/Bank 切换；
- 音频驱动、NMI/IRQ、RAM 新占用；
- CHR、调色板和动画时序；
- 存档格式和校验和；
- 任何 R4 改动。

验证最好由 Lua/测试运行器自动断言关键 PC、Bank、RAM、APU/PPU 状态和画面/音频存活；仍需人工覆盖手感、视觉、声音和完整操作动线。

### 11.3 模块完成定义

一个模块只有同时满足以下条件才可标记“已验证”：

1. 字段分母和只读/排除项已封口；
2. 开放字段均有 Codec 和边界校验；
3. 无修改往返与单字段差分通过；
4. 变长/共享资源通过容量和引用验证；
5. 保存后全新进程重开值一致；
6. 相关自动测试通过；
7. 必要的模拟器场景通过；
8. 用户说明、限制和验收清单同步；
9. 用户实际签收与实现侧自验分开记录。

## 12. 文档与决策管理

每个功能模块建议固定八节：

1. 范围界定；
2. 功能点清单；
3. 参考行为/目标规格；
4. 数据与写入规格；
5. 黄金对照或运行时采集清单；
6. 实现注意事项与禁区；
7. 用户验收清单；
8. 状态跟踪。

同时维护：

- 主需求：产品范围、功能 ID、全局状态；
- 数据字典：字段、编码、地址、证据、风险；
- 决策记录：为什么采用或否决某方案；
- 使用说明：当前实际可用能力；
- 开发记录：每轮已做、未做、验证、风险、下一步；
- 交接文档：构建身份、布局、运行时约束和复现命令；
- 提交历史：保持历史原貌，不用后来的认识改写旧结论。

文档中的“计划”“实现完成”“机器验证”“用户验收”必须分开，避免计划表被误读为交付事实。

## 13. 新 ROM 项目启动清单

### 13.1 开工前必须拿到

- [ ] 合法来源的基准 ROM 及 SHA-256；
- [ ] 平台、地区、版本、头部和 Mapper/映射信息；
- [ ] 可用模拟器和调试器；
- [ ] 若存在，参考修改器及其配置/码表；
- [ ] 目标功能优先级与明确不做项；
- [ ] 输出形态：ROM、IPS、工程文件、EXE/CLI；
- [ ] 至少一个可观察、可修改、可重开的低风险字段。

缺少唯一基准 ROM 时，只做研究和只读工具，不开始写入功能。

### 13.2 第一阶段应创建的文件

| 文件 | 用途 |
|---|---|
| `docs/需求规格.md` | 范围、功能 ID、状态和完成定义 |
| `docs/数据字典.md` | 资源、字段、地址、编码、证据和风险 |
| `docs/建设方案.md` | 分层、技术选择、阶段和门禁 |
| `docs/开发记录.md` | 持续记录真实进度 |
| `src/.../profiles.py` | ROM 身份与布局 |
| `src/.../rom_image.py` | 输入校验和地址换算 |
| `tools/golden_pipeline/field_registry.json` | 字段分母与证据索引 |
| `tests/test_profiles.py` | 基准身份和拒绝用例 |
| `tests/test_<first_codec>.py` | 第一个垂直切片 |

### 13.3 第一个里程碑

不要把“主窗口已经画完”作为 MVP。更可靠的第一个里程碑是：

> 用户提供一份精确基准 ROM，修改器识别它，读取一个字段，修改后只产生预期字节差分，可取消、撤销、保存、全新进程重开，并在模拟器中观察到效果。

完成这个里程碑后，再批量扩展相同风险等级的字段。

## 14. 从当前仓库复用到新 ROM

建议分三类处理：

### 14.1 可优先抽取

- ROM 不可变输入与范围读取；
- SHA-256、原子写文件、IPS 生成/应用；
- PatchOperation/ChangeSet 及重叠检测；
- 通用 ValidationIssue 和报告结构；
- 工程版本、操作日志和构建产物模型；
- 文件清单、打包自检和文档目录纪律；
- 黄金档案、字段注册表、覆盖率与完成门禁协议。

### 14.2 需要参数化后复用

- Bank 地址换算；
- ResourceGraph/BankAllocator；
- 文本表、调色板和通用 CHR 小部件；
- GUI 启动器、主窗口、脏状态和撤销/重做；
- 参考工具自动化驱动；
- 模拟器测试启动器。

参数化前要先识别当前代码里隐含的 iNES、8/16 KiB Bank、Mapper 194 和 DC 专属假设。

### 14.3 必须重新实现

- 目标 ROM Profile；
- 每类记录、文本、地图、脚本、图形、音频 Codec；
- 目标游戏业务规则和界面字段；
- 空闲区与保护区；
- 汇编补丁和运行时 RAM 规划；
- 目标模拟器场景与人工验收步骤。

不建议一开始就把当前 `fc_editor` 全部改造成“万能 ROM 框架”。先抽取边界清楚、已有两个使用场景的能力；只被一个游戏使用的逻辑继续留在游戏包内。

## 15. 常见失败模式

| 失败模式 | 后果 | 防线 |
|---|---|---|
| 先做完整 UI，后找数据 | 大量控件无法安全写入 | 先完成一个字节闭环垂直切片 |
| 只按文件大小识别 ROM | 错版本被误写 | 哈希 + 关键签名 + Profile |
| 假定 00/FF 区就是空闲区 | 覆盖延迟加载资源 | 静态引用、运行时轨迹、资源图 |
| Codec 重建整个表但不保留未知位 | 无关字节漂移 | 原始字节合并、差分门禁 |
| 批量改字段再看差分 | 无法确定真实映射 | 逐字段黄金用例 |
| 只验证“保存后当前窗口显示” | 缓存掩盖未落盘 | 全新进程重开 |
| 只测 ROM 能启动 | 深层场景仍可能损坏 | 定向模拟器场景和长程冒烟 |
| 失败时已写部分数据 | 项目状态不可恢复 | 候选副本、整体验证、原子提交 |
| 把参考工具的副作用也复刻 | 污染无关字节 | 归一化/否定证据单独登记 |
| 把机器自验写成用户签收 | 状态失真 | 两套记录和签核表 |
| 只按内部模块名和地址组织 UI | 初学者找不到入口或误解保存状态 | F1 任务向导、上下文直达、三级保存说明 |
| 只看离屏渲染或“无异常”就判定布局通过 | 真实中文字体与 DPI 下仍可能换行、重叠或裁切 | 使用正式 EXE 在目标 Windows 缩放下打开真实数据页，同时检查横纵滚动范围、底部操作完整性和中文最长标签；离屏图只作快速回归，不替代实窗验收 |
| 直接发布完整商业 ROM | 分发风险 | 发布源码、工具、报告和补丁 |

## 16.8 性能缓存与延迟页面初始化

### 16.8.1 参考功能保全先于优化

以既有工具为复刻对象时，应把参考工具的可达功能面视为最低兼容合同，而不是可选择的设计素材。性能、布局、安全和可维护性优化只能作为外层增强：同一入口仍应完成同一任务，同一保存应产生已验证的等价结果，同一取消应维持参考事务边界。不得因为控件拥挤、实现困难、担心误操作或已有更现代的交互，就删除、隐藏、禁用、合并或改义参考能力。

项目应同时维护“可见控件清单”和“可执行动作清单”。字段级字节映射只证明数据覆盖，不能证明菜单、右键、双击、嵌套窗口、导入/导出、清除、复制/粘贴及取消回滚等动作仍存在。每次优化前后应对当前模块做可达性差分，并把缺失动作视为回归；性能指标只有在功能清单、保存结果和事务语义不缩水的前提下才有效。

若参考行为存在破坏风险，优先增加预览、明确提示、草稿事务、完整撤销或可选增强模式，同时保留参考命令及结果。只有用户对某一具体差异作出明确授权，才能替换该行为；实现者不得把自己的安全判断记作用户决定。该原则适用于所有 ROM 编辑器复刻项目，并应进入需求、实现、测试、说明和发布五层门禁。

ROM 编辑器的容量预览经常需要“当前草稿替换后，全资源池会占多少字节”。不能在鼠标移动、表格信号或关卡切换时重新解码整个资源池。Codec 应以其绑定的不可变源快照为生命周期，惰性缓存原始/编码正文；资源发生写入、撤销、重做或链接重排后，工程必须重建受影响 Codec。UI 派生缓存则以“工程实例 + 单调修订号 + 资源 ID”为键，不以易漏判的控件状态猜测失效。

多模块桌面程序打开 ROM 时，只同步绑定工程并立即填充当前可见页；隐藏页应在第一次路由访问时初始化，后续编辑只标记为陈旧并在下次访问刷新。延迟初始化不能让自动化、插件或内部注册表读到空页面：页面注册表的索引访问和正常 UI 路由必须走同一个透明初始化入口。性能回归优先断言解码/刷新调用次数、缓存失效和最终字节一致性，墙钟时间仅作为同机观测值，避免把机器负载波动写成脆弱门禁。

含大量单元格编辑器的表格不应在记录数缩小时销毁控件、增长时重新创建。可以保留物理行并用逻辑行数隐藏复用，但所有新增、删除、读取、上限判断必须只操作逻辑行；严禁混用 Qt 物理 `removeRow`，否则会留下逻辑行指向空控件。缓存优化仍受 G2 约束：保存、撤销、重做、工程重开和全新进程重开必须与未缓存路径逐字节一致。

派生显示数据还要避免“隐藏的整 ROM 拷贝”：只读 Codec 若只读取切片，应直接接受当前 `bytes/bytearray` 缓冲区，只在返回单条记录时复制该小切片。名称、CHR 图块、剧情文本等高频查询应使用“工程修订号 + 类型 + 记录 ID”缓存；指针顺序或调用点扫描可在 Codec 的不可变源生命周期内缓存。多标签对话框可先构造轻量控件骨架，仅刷新首个可见标签，切换时再填充对应页面；已经关闭但仍属于同一工程修订快照的重型对话框只有在“取消”同时还原 ROM 和控件草稿时才可保留实例，工程对象或工作字节变化时必须重建。普通非事务工具若没有明确的草稿重置接口，应销毁窗口而只复用底层派生数据，不能为了二次打开速度让已取消输入复现。性能剖析应分别记录 ROM 解析、完整校验、主窗口激活和各重型窗口构造，避免只看总启动时间而错过某个页面的局部停顿。

性能审计还必须递归覆盖窗口内的每个 `QTabWidget`，分别记录首次进入与重复进入；只测顶级窗口会漏掉隐藏内嵌模块。大型只读数据浏览器宜先创建等数量占位页，让窗口先完成首帧，再按首次访问替换为真实页面；页面一旦建立即复用。代理模型的排序应在数据天然已有稳定顺序时延迟到用户首次点击表头，否则启用排序本身就会对尚不可见的全表执行比较。多个下拉框展示完全相同的大枚举时，应共享一个只读项模型，而不是为每个控件复制全部字符串和图标。

批量报表不得在逐行循环中调用“读取单项但内部解析全池”的 API。应增加一次校验、一次解析后生成全部派生记录的批量入口；长生命周期缓存若可能在事务尚未提交、修订号尚未递增时返回旧值，则宁可把共享结果限制在本次批量调用内。Codec 构造阶段已经验证和解码的记录、共享指针关系及别名索引应保存为不可变结果，后续 `record()` 只做查表。任何按当前指针顺序推导的显示缓存都必须在事务中旁路，并在工程修订号变化后失效。

## 17. 本文档的持续维护规则

本文档不是一次性总结，而是后续 ROM 修改器工作的长期方法基线。出现以下任一改动时，必须在同一轮同步评估并优化本文档：

- ROM 身份、Profile、地址换算或多版本兼容策略变化；
- Codec、领域模型、ChangeSet、工程文件或保存事务变化；
- ResourceGraph、空闲区判断、资源分配、扩容或运行时补丁变化；
- 逆向取证、证据分级、字段注册表或黄金对照流程变化；
- 自动测试、模拟器验证、人工验收或完成状态口径变化；
- 构建、打包、清单、交付物或跨 ROM 复用边界变化；
- 新 ROM 项目证明现有方法不完整、过严、过松或存在更好的实践。

维护时遵循：

1. 把新经验提升为通用原则、风险门禁、模板或检查项，不把具体游戏偏移混入通用方案；
2. 已被实践推翻的结论直接修订，并在项目开发记录中说明原因和影响；
3. 新增抽象必须至少有真实使用场景支撑，不为“万能框架”预设未经验证的复杂度；
4. 涉及当前产品用户行为时，同时更新用户说明；涉及模块状态时，同时更新需求状态和验收清单；
5. 每轮交付前检查“本次改动是否触及本文档”，将其作为完成定义的一部分。

## 结构动作黄金对照补充：不要把空记录长度当作分配长度

对指针表和共享池进行新增、删除或重排验证时，除了比较语义正文，还必须分别推导“正文长度”和“分配槽长度”。某些旧工具会让空记录正文仅包含结束符，却仍按一条完整记录的最小槽位推进后续指针。若实现只按正文长度压紧，首条空表看似可读，但所有后续指针都会产生固定偏移。

结构动作门禁至少记录：修改前后逻辑记录数、唯一正文数、别名拓扑、每类最小槽位、指针顺序、共享池实际占用、尾部填充策略、全新进程重开结果，以及容量不足时是否原子拒绝。直接字段的单字节黄金不能自动授权新增/删除；必须另做代表性结构保存，并用机器报告验证指针重排规则后再开放入口。固定槽记录缩短时还要明确处理旧正文尾部：按格式规定清零或恢复可信基线，不能简单保留当前工作区的残余字节；新增后删除应纳入逐字节可逆性测试。

若变长记录以“下一指针或固定池尾”作为唯一边界，重排后最后一条记录必须仍精确结束于固定池尾。可采用池尾右对齐并整体更新全部指针；不能把缩短产生的残余字节留在最后一条记录之后，否则重新解码会把残余误认为正文。实现还应从可信基线保存固定池起点，不能把一次缩短后抬高的最小当前指针误当成永久容量下界，否则随后补回原记录会被错误判定为超容。

相邻指针之差只描述当前排布，不能自动视为单条记录的永久容量。若参考程序会在保存时顺序重排同一 Bank 内的记录，复刻实现也应以该 Bank 分区为事务边界：先重编码分区内全部记录，核对总长度与固定分区尾界，再一次性写回连续数据和完整指针片段。界面应同时展示当前记录编码长度以及分区“已用 / 总容量”，避免产生伪超限。重排后必须重建指针缓存，并覆盖保存重开、连续编辑、撤销/重做及分区总量原子拒绝测试；单条记录仍不得跨越运行时代码能够映射的 Bank 边界。

同一编辑器页同时管理多类变长资源时，容量状态应跟随当前子页切换：地形页显示当前 Bank 和全部地形分区，部署页显示本关编码长度与全关共享池，触发页显示本关条数/字节与全关共享池。如扩展链接器将这些类别合并为统一 Bank 池，界面必须改为“本类占用 + 统一池已用/总容量”，不得继续显示已失效的旧分区上限。容量报告应同时记录语义正文字节、去重后字节、最小物理槽修正后字节和剩余容量，避免把可读的结束符正文误当成真实分配量。共享池物理尾必须以同 Bank 下一段已验证代码/数据的首地址为界，不能把当前正文末尾误作容量尾；若扩容 Hook 位于旧池内部，链接时须先捕获和搬移旧池语义数据，再覆盖 Hook，而不是要求该位置永远为空。若同一类资源只有多个被其他数据隔开的安全区，Codec 必须显式建模分段池、按段写补丁和工程覆盖范围，并用确定性装箱选择记录；不得用首地址加总容量形成伪连续区，更不得清空中间归其他模块所有的数据。

当“首次编辑的临时托管池”和“正式扩展 Hook 空洞”复用同一安全区域时，容量规划不能只拿当前输入与出厂 ROM 比较空洞。直接重开的派生 ROM 可能已包含工具自身的临时池。规划流程应先按现有指针完整解码并捕获语义，再仅清理经过身份验证的自有托管范围，最后安装正式 Hook；同时用“临时编辑→保存→全新进程重开→首次规划”覆盖这一迁移路径。不能把未知占用当作自有池清理。

## 固定容量编辑的当前构建验收补充

参考黄金证明字段含义后，仍应针对当前产品构建执行一次完整的 GUI 到磁盘闭环，而不能只调用 Codec。验收脚本应通过真实控件完成选择、编辑、暂存、窗口确定或取消、另存 ROM 和全新工程重开；预览开关等非持久交互要断言既不改变工作区字节，也不产生字段草稿。对于固定容量列表，至少执行一次“删除一项→保存重开→补回原项→再次保存重开”，并比较补回产物与编辑前产物的整文件哈希，以发现表尾填充、排序或结束符漂移。

危险参考动作若已有确定性证据证明会跨越多个全局区，但尚无安全重排模型，应保留入口语义而明确禁用：界面显示容量范围和禁用原因，自动验收断言点击零写入；另选一个确实需要扩张的合法字段修改，验证容量错误发生时整笔事务原子拒绝且表单草稿仍保留。机器验收报告必须同时记录输入哈希、派生输出哈希、截图与逐项布尔结论，并与用户最终签收分开表述。

产品侧闭环不能替代参考版动作黄金。对于图像拼图、上传、清除等跨图库操作，即使当前产品能完成草稿、保存重开、取消和撤销，也只能标为“产品实现已复验”；只有参考程序在隔离副本上执行同一动作并得到可解释的保存差分，才能升级为“参考版已对齐”。参考程序因完整性级别或窗口不可控而未生成差分时，应归档尝试和原因，保持动作门禁，不把无响应点击算作 no-effect 证据。

尚未执行的参考动作可以先固化为 discovery 配方，但报告必须把“已准备”和“已晋级黄金”分开计数。准备态配方需锁定文件哈希、明确 `case_kind=discovery`，并保持 `expected_offsets`、`required_offsets` 为空；只有取得真实落盘差分、人工解释全部副作用并完成冷重开后，才能复制为正式黄金配方并登记偏移。任何准备态配方被提前填入必写偏移，都应使报告失败，而不是自动扩大可写范围。

正式桌面构建的最终回归还应独立于源码内嵌控件测试：先固定 EXE 与只读输入哈希，复制隔离工作文件；若原生打开对话框无法被可靠定位，而产品明示支持文件关联或命令行文件参数，可用该公开入口加载隔离文件，仍须从正式 EXE 的可见窗口完成编辑、应用、原生保存、关闭和全新进程重开。保存时选新目标，不覆盖输入；记录精确字节差分、三份文件哈希和重开后的控件值。此路径证明当前打包程序的通用落盘闭环，不能替代各模块尚未执行的错误提示、参考黄金或用户签收。

容量和坐标的原生错误反馈宜使用两份分别构造的**合法**隔离输入：一份刚好低于共享池上限，再由可见控件添加一项跨越上限；另一份将记录放在原地图的边缘，再由可见尺寸控件缩小地图，且预先确认缩小后的地图压缩大小仍在容量内。这样能够分别触发目标错误，不受其他错误先后顺序干扰。记录错误文案、尝试应用后的草稿状态、工作区改动字节数及磁盘输入哈希；不能把“出现错误框”单独等同于原子拒绝。

## 原始证据与可变草稿分离

若可写权限依赖“原地址 + 原字段值”与资料一致，窗口打开时应冻结可信输入快照。连续修改同一控件时，证据比对始终针对该原始快照；对当前草稿则分别重验指令结构、索引范围和目标记录完整性。不能因为第一次合法修改改变了草稿值，就错误地撤销原位置的可信性；也不能仅凭原始证据放行被其他编辑破坏的当前结构。验收至少覆盖“第一次更换→第二次更换→改回原值”、保存后全新工程重开、精确字节差分及未获证位置仍拒写。

旧资料中的地址表可批量提取，与当前 ROM 的预期操作码和字段值做“精确匹配 / 仅相邻匹配 / 附近无匹配”分类，并记录资料与 ROM 的哈希。相邻匹配只说明存在值得进一步调查的候选，不是地址修正或写入许可：同一资料表若还有其他不匹配，尤其不能以单项看似差一字节概括版本差异。必要时继续取得参考程序对相同输入的实际保存差分与冷重开结果；程序没有进入目标界面或没有生成落盘差分，不应被标为 no-effect 黄金。

验证“新增→改值→删除”的整文件可逆性时，先判断首次写入是否会把旧布局迁移或归一化到工具托管布局。若会，应在隔离副本中构造语义等价的空操作归一化基线，确认所有逻辑记录未变，再把删除后的结果与这个基线逐字节比较；直接要求它等于迁移前 ROM 会把预期的指针重排误报为残留写入。同时单独断言原始输入哈希未变，并列出迁移带来的固定差分，避免用“归一化”掩盖真正的额外改写。

## 运行时预览必须生成隔离且可校验的场景夹具

需要在模拟器中预览某个编辑对象时，仅导出普通 ROM 并启动模拟器不等于功能完成；普通流程可能没有可进入的关卡、没有目标对象或装备的仍是存档里的旧对象。应先用运行时读跟踪或反汇编证明“场景选择值→运行时记录→ROM 配置表”的完整链路，再生成只供预览的 ROM/存档对：ROM 副本仅修改测试对象的绑定，存档副本同时更新活动块和镜像备份，并按原格式重算校验。源 ROM、源存档和当前编辑工程必须保持逐字节不变。

夹具验收至少保留四级证据：生成前后的哈希与精确差分、备份校验有效、模拟器内目标对象/选项可见、实际进入动作或动画画面。若只能看到标题、菜单或普通战场，不得宣称目标动画通过。产品应把夹具写入明确的输出目录，使用与测试 ROM 同名的模拟器存档，并在界面提示进入路径；自动机器验收与用户主观签收仍分开记录。

## 全模块写入分布不能直接当作空闲区

旧工具的保存差分应从保存前后 ROM 重新计算，并剔除已证明的固定归一化副作用；失败、超时、冷重开不一致和待发现用例不能进入正式分布。聚合报告中的连续区间只表示“这次操作观察到旧工具写过”，不能证明整段由该字段独占，更不能据此跨模块分配。

解除等长限制前，必须同时证明：入口表或指针表、记录结束规则、共享别名、固定池尾、增长与缩短行为、内部跳转/子指针重定位、容量不足原子拒绝，以及保存后全新进程和必要的运行时回读。只有这些条件闭环后，才能把观察区间提升为资源所有权；否则继续保持原位、等长或只读。全模块报告应同时列出“已有合格保存对”和“仍缺动态证据的模块”，避免把覆盖率误报成完成率。

对已经证明资源所有权的变长脚本池，应优先采用“整池解码—唯一记录压实—指针表重建—内部引用重定位—尾部清空”的确定性重排，而不是只把目标之后的数据向后挪。前者能回收缩短记录产生的所有碎片，并天然维持共享指针别名；写回前要建立“旧指令边界→新指令边界”映射，跨记录绝对跳转也必须通过该映射。目标被删除、落在非指令边界、任一记录无法完整解码或总正文超过固定池尾时，整个事务必须拒绝。容量提示应报告整个池的实际已用/剩余量，不再把相邻指针间距误称为单条记录的永久上限。

面向用户的全局容量总览必须采用“物理池身份”而不是“页面行”汇总：同一池被普通名称、战斗名称或多个标签页引用时，只计一次；不同 Bank 即使业务名称相似，也不得合并。固定表与可重排池分栏统计，固定表始终显示为不可扩展，不能把零填充、重复指针、记录间隙或差分包络纳入剩余。报告应直接读取当前工作草稿的指针与唯一物理记录，并提供刷新入口；所有剩余量都必须附带所有权说明，明确只能在同池内部使用。若某区域只有静态地址或旧工具写入证据、尚无池尾和重排器，就只能列为固定/待验证，不能出现在可用容量合计中。

当一个运行时资源目录把多种数据库表装入同一 Bank pair 时，应先建立“目录项→指针表→逻辑记录→结束边界”的完整资源图，再允许任何子模块变长。复核算法至少要能够把未修改 ROM 解析后重新序列化，并对管理区逐字节零差异；还要对一项前部资源增长和一项中部资源增长的旧工具样本重复该验证，证明所有后续目录入口和内部绝对指针都会正确重定位。界面可以按业务模块拆分显示占用，但剩余容量只能归属复合物理池，不能重复分配给每个页面。

数据库的日常容量展示不得再集中成一个容易误读的总入口。六个顶层模块各自嵌入紧凑容量栏，只枚举本模块的固定结构和物理池；详细窗口也必须锁定为当前模块，不能默认把其他模块的剩余并列成可互借总量。底层报告仍以稳定 `pool_key` 去重，用于完整性检查和研究审计，但产品界面只呈现局部所有权。固定结构统一表述为“可改值、不可增长”；可变长池显示本池已用、容量与净增长，且必须在工具提示和明细中写出共享者。

兼容旧修改器应区分“运行语义一致”和“落盘算法逐字节相同”。字段编码、值域、别名关系及游戏读取结果必须由旧工具黄金样本和运行时代码共同约束；旧工具若通过搬移大量后续区段完成保存，产品不应为追求差分外观而复制这种高耦合写法。已有可靠原位字段就等长写入，已有边界与重排器的资源只在自己的池内整理；只有存在经过执行验证的运行时选择器时才允许迁到登记的扩展资源。每种迁移至少保留整 ROM 差分白名单、活动描述符验证、直接 ROM 重开、事务撤销、受保护区域认证和模拟器基线，证明修改没有落入其他数据库模块。

## 静态配置预览不能伪装成运行时状态模拟

当静态关卡记录只保存“运行时槽号”，而槽内容由初始表和事件建立时，必须分别验证游戏运行时语义与参考编辑器的静态读取口径；两者可能使用相同字节却作不同解释，不能只凭其中一方的反汇编结论替代另一方的逐关界面实测。至少选择一个中期关卡和一个后期关卡，逐行读取人物/机体下拉内容，再把差异与前置入队、离队、换人和换乘事件的原始参数对应。只抓一个后期关卡再推广为全局固定图例，会掩盖事件变化并制造看似完整但错误的人员表。

若参考工具按事件建立静态预览，应先确认它累计的是全部运行时状态，还是只读取某一类“入队/生成”记录；不能擅自把离队、换乘等游戏语义加入参考工具本来没有的静态计算。还要沿事件加载器追踪全部物理分区，不能只因一个 Codec 能解出部分关卡就漏掉其他 Bank。从初始表生成第一个快照后，把目标类型的每条物理事件指令归到可证明的关卡与阶段顺序，并在下一个关卡快照前应用。共享脚本可能同时出现在多个上下文中，必须以物理身份去重，不能按上下文数量重复执行。派生快照的缓存键必须包含初始表、全部事件入口和全部相关事件正文，确保修改、撤销、重做或重排后自动失效；人物名称、机体图标、属性跳转和工具提示必须共用同一快照，不能各自维护硬编码名单。

人物数据库还需区分“物理指针复用”和“用户层联动”。旧修改器 M06 冷启动样本已确认，人物属性和人物台词即使有数十个逻辑 ID 指向同一物理记录，编辑其中一个 ID 时也会自动拆分目标，其他 ID 保持原值。人物台词记录自带三组 `FF` 结束结构，因此可以按逻辑 ID 解包、修改目标、重新去重并在 Bank `$06` 固定代码 `$B510` 前原子重建。Bank `$24` 的属性、普通名、战斗名等八个子区由头部动态入口共同管理；产品现已按旧版接通完整复合序列化器，人物普通名、战斗名或属性增长时会整体重建八类资源、更新入口和内部指针，并动态重绑定后续模块。界面因此直接显示 `9529/15184 B` 的真实共享占用和 `5655 B` 可写余量，不再显示名称 `395/395 B`、属性 `477/477 B` 的假门禁；整体越过固定代码 `$BF40` 时才原子拒绝。

同样的方法也适用于跨业务页面的连续尾区。若“人物头像”后面紧接“机体战斗外观”，容量所有权就属于两张指针表和两类正文组成的复合块，而不是头像页或机体页单独拥有。审计器应同时按真实的定长/变长规则解包两个资源、按逻辑 ID 顺序去重重建，并以后一段固定代码作为共同硬边界；只有整个区间逐字节还原且目录入口一致，才能显示动态剩余。若产品写入器尚未同步支持两资源后移，界面可显示“已解析但增长未开放”的诊断值，但不得把它纳入可写容量合计。

当用户确认参考工具把复制粘贴得到的相同记录视为独立对象时，产品不能继续暴露“同时修改共用记录”选项。正确实现是写时复制：解包全部逻辑 ID，只替换目标记录，重新去重后原子写回；若后续资源地址因此改变，所有运行时目录、读取器、验证器、撤销和重开路径必须同时跟随动态入口。图像配置记录的独立性不等于 CHR 像素数据独立，后者若仍指向相同物理图块，继续单独提示实际影响者。

若条件加入仍依赖无法静态确定的存档标志，应保留真实空槽并说明边界，不能为了让全部部署都有图片而填入存档快照或单关固定名单。图标变异探针只能证明图形来源，不能证明驾驶员；可见文字必须逐行截图或读取控件。测试至少覆盖一个已知逐关名单、入队事件参数修改后的后续关联动、共享指令只执行一次及空槽不伪造图标。该预览模型只影响解释和显示，不得反向改写 ROM 事件或部署正文。

## 参考编辑器置灰不等于游戏运行时无能力

参考程序把字段置灰、保存时强制常量或没有入口，只能证明参考程序的编辑范围，不能直接推出游戏不读取该字段。若产品准备把它作为增强能力开放，必须同时向下追字段消费代码和向上追调用入口：证明字段比较发生在分流前还是分流后、哨兵值的准确含义、哪些阵营/对象能进入该处理程序，以及最终动作如何分派。界面应使用运行时真实范围命名，例如 `$FF` 只跳过人物编号比较而触发入口仅来自我方行动时，应写“任意我方人物”，不能写会暗示敌我皆可的“任何人物”。增强字段还必须覆盖非哨兵匹配/不匹配、哨兵多值匹配、保存重开及原始字节不串改。

## 参考编辑器可选不等于 ROM 对象有效

参考程序把某个编号列入启用状态的下拉框，只能证明它允许用户选择，不能证明编号背后存在合法记录。对指针型目录必须逐项验证目录长度、指针目标、目标记录边界及运行时消费者；若干编号实际别名到另一类数据表时，产品应只展示已证明有效的对象，不能为了表面 1:1 复刻而开放会把其他数据解释或写成当前类型的选项。归档控件树用于证明参考行为，ROM 指针与运行时代码用于决定产品安全边界，两类证据应同时写入模块记录。

超长枚举的交互也不能照搬系统默认行为。应用层应统一禁用会忽略 `maxVisibleItems` 的原生超长弹层，把所有下拉框限制在固定可见行数内并保留滚动条；模块单独设置更小上限时应继续尊重。Windows 下拉框还可能在鼠标按下时打开弹层，并把同一次按压经过其他条目后的松开当作选择，造成“只移动鼠标就改值”。应拦截且只拦截这次打开弹层的松键，保持弹层与原值不变，让后续明确单击才提交选择；键盘选择和已经打开后的正常点击不能被破坏。当用户需要频繁访问首项、而当前高编号会让弹层自动居中时，可在特定控件每次展开后明确回到首项，同时保持当前值本身不变。测试至少断言选项全集、不可用编号不存在、全局及模块弹层可见行上限、首次按移松零修改、第二次点击生效，以及需要首项锚定控件的展开滚动位置。

名称由问号、破折号或其他占位外观字符组成时，也不能仅凭文字形态判断记录未分配。应结合独立 ID、指针、引用位置和运行时比较方式区分“有效的未知身份”与真正空槽；若该 ID 能被脚本或规则正常引用，界面应忠实显示 ROM 名称并允许选择，不能擅自改写为“未命名/未分配”。真正空名称仍可使用明确的空槽说明，两者必须有分别的回归样本。

## 先区分参考工具语义与目标 ROM 的重复指针

看到多个逻辑 ID 指向同一条物理记录，只能证明目标 ROM 当前存在重复指针，不能直接推导“参考修改器以共用记录方式编辑”。必须分别统计参考 ROM 的有效记录与空槽、检查参考工具的保存循环，并用真实保存前后样本确认它是联动改写、按 ID 拆分，还是整体重建。空白/未使用槽共用一个结束记录尤其不能当作有效对象共用语义。产品文案应写“当前 ROM 重复指针”，除非已有一手交互与落盘证据，否则不得写成“旧修改器共用名称”。

## 满载重复指针池的直接编辑应采用写时复制

当目标 ROM 让多个逻辑 ID 指向同一条变长记录，而且原池已经满载时，直接修改其中一个 ID 不能沿用“改写物理记录”的语义，也不能把当前池尾误当成扩容后的永久上限。若运行时读取入口已经有经过验证的资源选择器，可为该资源建立独立 Bank pair：保留一张游戏实际读取的活动指针表，再保存一张仅供编辑器恢复逻辑身份的规范指针表；首次迁移时把每个逻辑 ID 展开为独立记录，之后按目标 ID 写时复制并重排。该兼容策略只描述目标 ROM 的安全写入方式，不应反向宣称参考工具本来就提供共用名称编辑。

扩展 Bank 不应成为首选捷径，但也不能仅因两个资源在当前 ROM 中可被同一运行时窗口访问，就自行认定它们可以共享容量。旧修改器机体名称保存循环的独立上限为 `$BEB0`，初始配置另有独立的 `$BF00` 保存循环；旧版未扩容可增长来自名称资源自身 `0x1A2D`（6701）字节的净增长余量。当前推荐 ROM 没有原样保留这段物理空间，因此机体名称采用“原生名称池内重排，超限后最后分配独立名称 Bank pair”，不再借用部署尾部。容量语义必须严格复制旧版额度：把当前 255 个逻辑名称独立展开得到 `1456 B`，再加 `6701 B`，独立池有效容量固定为 `8157 B`；不得因为实际申请了 16 KiB Bank pair 就把其全部余量开放。通用的动态分界方案只允许用于已有明确旧版保存差分和运行时所有权证明的资源；地址相邻、指针可达或字节为零均不足以授权跨模块借用。

该迁移必须有可识别魔数、资源登记、运行时选择器校验、重开探测、容量报告、事务撤销和完整性检查；不能只把数据写进“看似空白”的 Bank。`DCUNAME2` 在资源头中保存有效正文容量，重开时只恢复该跨度；旧 `DCUNAME1` 继续按原全跨度读取，保证历史派生 ROM 兼容。若其他模块没有已验证的运行时重定位入口，仍应保留它自己的池内重排和真实容量门禁，不能因为另一个模块已经能扩容就推断它也能共用同一空间。容量界面还必须把“现有字段可编辑”和“允许净增长”分开表达，避免用“剩余 0”误导成整页不可编辑。

## 图形外观不能替代属性位证据

同一 CHR 图形可能在不同图库、地图或规则下承担不同语义。属性编辑器必须把 ROM 字段与渲染外观分离：可用外观提示调查候选，但不得因“看起来像水面、道路或障碍”自动勾选属性，更不得在用户修改无关字段时顺带写回推断值。若参考工具的控件值与输入 ROM 原始字节冲突，应先记录冲突并追踪运行时消费者；在没有运行时证据前，以可定位、可复现的原始字段为读写真值，不把旧工具显示错误升级成产品规则。

## 图像导入必须把预览、资源写入和自动拼图分开取证

参考编辑器中的同一个“上传”按钮可能因复选状态进入完全不同的路径：一条路径只更新内存预览而不形成保存差分，另一条路径同时量化像素、分配 CHR 图块和重建可变长拼图脚本。产品侧能够保存重开，只能证明自己的安全实现闭环，不能反推参考工具也采用相同的缩放、切块或脚本模板。

对“尽量少用碎片”这类可验证目标，不应以某个贪心找块顺序当作完成。可将问题建模为“用最少个 8×8 方块覆盖全部非背景像素”：每次选取最左未覆盖像素，利用方块可向右规范化到该像素的性质，只分支其至多八个 Y 起点；再用两两不可被同一方块覆盖的像素打包数作安全下界，配合状态深度记忆化剪枝。只有搜索完整结束才可标记“全局最少”；超过节点上限时应拒绝导入，不能悄悄退化为未证明的次优结果。图块写入与脚本替换必须同属一个草稿事务，偏移后容量不足时两者一起保持原状。

“最少图块”还必须区分放置数与资源字典数。若脚本只能在固定网格放置整块且没有翻转位，非空格数量已经是最少放置数；但图库仍应把像素完全相同的格子驻留为同一资源，并让多处放置复用同一编号。此时对全部非空块建立内容哈希/内容字典，所得不同内容数就是该脚本模型内可证明的最少图库资源数。不得宣称使用脚本不支持的镜像、任意像素偏移或叠加分解来进一步优化；状态提示和容量校验也应明确统计的是“唯一图库图块”还是“画面放置”。

自动分块前的尺寸归一化也必须有独立证据。若参考样本只证明固定尺寸原图直接分块，产品就不能把“任意尺寸等比缩放并居中”描述成参考规则，因为缩放会同时改变像素、边界和锚点。严格模式应在创建任何资源草稿前校验原始尺寸并原子拒绝不匹配输入；若另设兼容缩放，必须作为明确的增强入口，与严格导入分离。

图像“清除”必须同时审计资源层与引用层。若参考保存差分同时改写 CHR 和拼图脚本，产品只清图库会留下仍引用空白块的陈旧脚本，只清脚本则会留下不可见但继续占用的资源。主入口应把两者组成单一草稿事务，并为各层使用明确的空记录哨兵；同时保留“仅清脚本”和“仅清图库”作为名称不同的高级操作，避免同名按钮出现三种隐含语义。测试至少覆盖两层同时变化、取消零落盘、保存重开一致以及共享图库边界。

压缩导入还要检查写入区间之外的字节。生成 N 个图块并不自动授权清零从 N 到图库末尾的空间；只有保存前后差分证明尾部被清除时才能这样做。默认安全规则是仅覆盖实际生成的连续区间，偏移前缀和未使用尾部原样保留，并分别用非零哨兵测试。若参考工具的普通上传只更新临时预览而没有动作专属保存差分，主入口也不应擅自升级为持久导入；持久的单图块或整图库替换应放在名称明确的高级入口。

在桌面修改器中，“紧凑”必须同时满足信息邻近和可识别性。应先移除状态条、按钮组和字段之间的无效留白，再缩小控件；不能靠降低文字/边框对比度营造“轻”的观感。同一容量、草稿或状态信息不应在一屏重复占行：保留一个靠近决策点的主入口，其余状态可作为非可见诊断数据；与此同时，不应为了“填满”而增加无功能文字，可通过主预览、表单和工具组的锚定与对齐建立节奏。可用操作应使用比面板背景更深的文字和边框，禁用态则同时降低文字、边框和底色对比。高密度色格类控件需在目标 DPI 下计算“总边距 + 格宽 × 列数 + 间距 × (列数-1)”，避免固定窗口比内容小几个像素而造成粘连或裁切。

逆向自动切块时，至少分别保存原始图片、参考保存前后 ROM、目标 CHR 字节、生成脚本及脚本解码后的坐标。固定网格去空块可以用逐格扫描证明；任意像素碎片还必须检查裁取后是否会从工作图清除已消费像素，因为这会改变后续重叠块的内容。单张复杂图片通常只能证明最终坐标和消费结果，不能唯一确定“选择下一块”的启发式；应增加孤立像素、相邻、重叠、边界和透明色合成图片，以排除多个算法在同一样本上偶然等价。未锁定唯一规则前，产品应把现有导入称为增强能力或部分实现，不用猜测性贪心算法冒充 1:1。

对枚举字段还要分别验证每个字段的值域，不能因为相邻数组布局相同就共用选项。例如一个数组可能只表达 `$00/$01` 通行状态，而相邻数组才表达多档移动消耗。Codec 解码和写入校验、界面选项、工具提示与测试必须使用同一值域；至少保留完整记录区快照、一个争议样本的精确原码/解码结果，以及非法值拒绝测试。

通用名称服务里的“无对象/特殊上下文”不等于每个引用该对象类型的字段都允许编号00。窄场景下拉必须以该字段的参考映射、现有记录全集和运行时消费者共同确定值域；若参考控件使用“索引+1=ROM编号”，界面就应从01开始，而不是直接复用00—FF通用枚举。为兼容旧版本曾产生的越界值，读取时应保留原始记录并显示明确警告，保存前要求用户重选，不能静默改成首项。审计同类控件时也要区分真正错误与合法哨兵，例如店员00、事件条件00或不限人物FF必须按各自上下文独立判断。

连续数据的“视觉分段”也不能替代运行时记录边界。若一段看起来像“4字节头＋多个数组”，必须跟踪运行时基址和各读取偏移：程序可能以数组首地址为记录基址，并把身份头放在记录末尾。应记录指针表的全部候选、至少一次真实加载时的 CPU 地址→PRG 偏移→文件偏移转换，以及关键字段复制到 RAM 后的消费者。只有这样才能避免把当前图库的末尾身份头与下一图库的数组错误合并；固定哈希只能证明字节未变，不能证明分组正确。

## 同一对象中的定长记录与可变长资源必须分开建模

“机体”这样的界面对象并不等于 ROM 中的一条连续可变记录。当前机体属性是运行时固定 16 字节结构，战斗外观配置归一化后是固定 10 字节；名称、主体拼图和碎片拼图则分别由指针表进入 `$FF` 结束的可变长池。界面可以把它们组合展示，但写入层必须按各自所有权处理，不能因为脚本允许增长就放宽属性记录长度，也不能因属性定长而把脚本限制为原长度。属性表中的重复指针属于物理去重，不得暴露成用户层联动限制：默认 ROM 第一次修改重复记录时，选择器 `$71` 切换到镜像核心 Bank pair，指针表重建为 255 个逐 ID 独立的 16 字节记录；直接 ROM 重开、工程重放、撤销和后续完整机体分区都必须保持该独立语义。

可变长池的容量提示必须先从活动扩容计划解析实际 Bank 对，再用运行时资源目录和完整 256 项指针验证全部记录，最后按真实池拓扑计算已用/剩余量。48 KiB 机体布局的主体与碎片共享一个正文池；64/80 KiB 布局把两类脚本拆到独立 Bank 对，不能把两者的剩余量混报。验收至少包含一条记录增长、另一条记录缩短、指针重排、保存后全新工程重开、撤销，以及越过池尾时工作区逐字节不变；界面显示的数字与该验证器返回值必须来自同一数据源。

当某项可变资源位于复合 Bank 的最后一段时，“从当前根到 Bank 尾”的字节数只能称为其他资源不变时的条件上限，不能显示成该资源独占容量。常驻状态应优先展示本资源正文占用和整个复合 Bank 的真实共享余量；条件上限仅放在详细说明中。不同 Bank、不同分段池或迁移规则的容量不得合并到同一个悬浮框，也不能共用一句迁移状态。

所有容量界面都必须明确写出归属：共享池列出具体共用的数据类型或记录集合，独立池明确写“不与其他数据区共用”。“共享池”“共用”“总剩余”等没有共享对象的孤立文案不作为完成状态；多个物理 Bank 若不能互借余量，也必须明确标为彼此独立。

## 派生 ROM 的重映射编号必须结合脚本身份命名

扩容或改版 ROM 可能把原编号脚本复制、搬移或重映射到参考名称表未覆盖的新编号。此时不能只因名称表缺项就显示为“空槽/未命名”，也不能只凭一个调用编号猜名称。应同时比较完整指令结构、资源参数变化、循环目标重定位和调用位置；结构与已知原记录一致而地址/配色发生派生变化时，可采用“原语义名称＋派生/重映射说明”。参数开放仍按指令字段逐字节取证：固定长度不代表所有操作数都可改，例如三字节状态/偏移指令可以只开放已确认的有符号偏移，锁定操作码和状态选择器。多颜色变长参数应依据指令自带数量动态生成控件，并采用可换行或网格布局，不能把九个字段挤进为三色指令设计的一行。

## 脚本效果预览必须区分离线可重放语义与运行时依赖

为可变长动画或事件脚本增加即时预览时，应直接读取编辑窗口的草稿层，不能要求先写 ROM，也不能让关闭预览产生事务。预览解释器应设置指令步数、帧数和循环目标边界，循环只允许跳到当前已解码指令边界；非法或跨记录目标必须停止并提示，不能在 UI 线程无限运行。图块、调色板、组图和已验证帧规律应复用正式 Codec 与项目工作副本，避免另建一套漂移的资源解释。

离线预览无法天然获得事件参数、战斗 RAM、动态地址表或运行时生成图块。对此应保留占位、稳定默认位置及明确说明，并把结果称为“离线预览”而非“实机模拟”。只有通过隔离 ROM/存档夹具在模拟器中完成调用链与画面对照，才能宣称运行时一致。测试至少覆盖未保存草稿立即生效、播放控制、有限循环、未解析资源降级、关闭零写入，以及正式项目工作区逐字节不变。

## 性能验收必须测量用户可见完成时间

构造函数、Codec、离屏窗口和页签槽函数的计时适合定位热点，但不能直接代表用户体验。正式验收必须使用最终交付形态（例如 PyInstaller 单文件 EXE），从真实鼠标/键盘操作开始计时，直到目标窗口已绘制完整内容，而不是只等窗口句柄、标题或空白外壳出现。首次打开、重复打开、冷启动、ROM 载入和内嵌页切换应分别记录；截图或可访问树采集本身的固定开销也要注明。

若实测先出现白窗再填充内容，应把“内容完整出现”作为结束点，并明确保留白窗问题，不能用后台已经构造完对象或窗口标题已变化宣称完成。优化方案也要用相同现场方法前后对比：把工作搬到文件选择框期间、启动后后台线程或另一个页面，只是转移卡顿，不能算性能提升。后台预热只允许处理线程安全的不可变数据或模块导入；Qt 控件创建与绘制仍必须在 GUI 线程，并需验证预热没有与 ROM 解析争用 CPU/GIL、没有让启动页或文件对话框变慢。

## M05 拼图动作黄金约束

机体拼图和碎片拼图不再只以“可解码、可重开”作为兼容标准。`tools/audit_m05_puzzle_golden_parity.py` 直接读取 17 份已晋级的旧修改器黄金用例，并把当前动作函数的结果与 `requested_value` 逐字节比较。机体移动先解码完整放置范围，再按阵营限制到旧版 16×16 战斗画布；越界动作返回原脚本。碎片整体翻转先解码绝对放置，按旧版水平轴 `x'=120-x` 或垂直轴 `y'=122-y` 变换坐标和翻转位，再用已验证的紧凑指令族重编码。

保存字节黄金不能替代窗口交互黄金。拼图类模块还必须把每个按钮的左键、右键和键盘激活、列表逐项选择/双击/右键/键盘导航、输入框边界与平台编辑路径、下拉框全项选择以及动态启用条件登记为稳定动作 ID。会改变草稿的按钮应从重新打开的子窗口开始，避免前一动作污染后一动作；大型机第二图库、碎片图库或列表等条件控件必须从当前 ROM 扫描真实可用记录，不能把某个历史 ROM 的行号硬编码为通用前置条件。最终取消外层事务并以完整 ROM 零差分收门禁。

兼容例外只有用户明确要求保留的碎片最少图块导入：旧版复杂样本按顺序裁切使用 23 块，产品继续使用可证明全局最优的 22 块覆盖。此增强只改变压缩导入的分块方案，不改变画布坐标、源图尺寸、导入偏移、未使用图库尾部、容量原子拒绝或确定/取消事务。

图库右键导入不得复用隐藏控件的初始值作为起点。鼠标按下时先把画布命中的本地图块号写入选择状态，打开菜单后再将其换算为当前图库页内偏移；主体双图库必须区分绝对本地图块号与当前页偏移，碎片连续图库则直接使用 `$00—$7F`。导入容量检查、图库草稿和脚本替换必须在起点换算之后执行，保证偏移前区域逐字节不变。需要逐项构造碎片脚本时，应把“选中图块”和“自定义十六进制图块号”都作为明确入口，取消或非法输入必须零草稿。

对“未扩容”不能直接等同于“变长记录不可写”。如果参考保存镜像显示资源目录本身包含可移动的后续指针表和活动末尾，应把整个原生 Bank 视为一个有界动态分配区：保存时按逻辑记录顺序重建指针，重复指针采用写时拆分，移动后续子目录，并以运行时目录给出的 Bank 尾作为唯一容量边界。必须用参考版保存前后镜像验证目录项、目标记录、后续指针平移和活动末尾；固定常量只能作为初始布局，不得继续充当重开后的边界。外部扩容区只能在原生总容量确实不足后再分配，不能成为普通编辑的先决条件。

## 引申交互与共享容器的保全规则

功能对照必须沿真实操作图向下遍历，不能只比较顶层页面或字段。左键、右键、双击、上下文菜单、菜单动作、二级/三级参数窗、文件选择、预览播放器、确定/取消、外层取消、撤销/重做和保存重开都属于独立验收节点。参考控件枚举用于发现入口，动作回归用于验证结果；二者缺一不可。每个自定义鼠标处理器、`customContextMenuRequested`、`itemDoubleClicked` 和 `doubleClicked` 连接都必须在全功能交互矩阵中有对应证据。

当旧版一个外层目录项与新功能地址冲突时，必须继续分析其下属资源，禁止直接禁用整个页面或整行。容器元数据写入与实际文本、图像或规则子资源要分别判定；只越过会覆盖已保留功能的物理写入，仍安全且独立的子资源继续开放。M10 的无效商店行即按此原则处理：28 个元数据动作与地图事件指针表冲突而越过，63 个独立对话字段恢复可写。

正式构建脚本的输出目录和工作目录必须是真实参数。正式 EXE 被用户进程占用时先在隔离目录生成、归档检查并隐藏自检，不能让隔离构建误写正式路径；只有目标实例退出后才覆盖正式文件并同步校验文本和映射表。

## 递归状态探索与分母闭合

静态 HWND 数量、字段数量和窗口截图都不能单独构成功能分母。参考版审计必须建立“窗口状态—操作—结果状态”图：对标准控件枚举左键、右键、双击、键盘、逐项选择和边界输入，对自绘控件按网格/区域执行左键、右键、双击与拖拽，对菜单执行全部非分隔命令，并为同一控件的显隐/启用变化建立反向触发任务。任何操作产生的新窗口、菜单、控件或状态都必须回灌探索队列。

`tools/report_legacy_interaction_frontier.py` 负责从全部保留快照生成稳定 `action_id` 和待执行前沿；执行证据单独记录，生成候选绝不能自动算通过。只有所有动作均有旧版观察、新版映射、保存/取消影响及必要的 ROM 差分证据，且连续完整遍历不再产生新状态，探索门禁才允许闭合。不同 ROM 版本、记录类型、空槽/已用槽、共享/独立记录和容量边界必须作为状态维度重复遍历。

旧式自绘页签不能依赖控件文字或标准 Tab 消息。应先只点击页签头部带，保存每个新页面的可见控件签名和可复现坐标；完成所有页签定位后，第二阶段再进入页面执行右键、双击和记录选择。若边探索边识别页面，列表选择导致的字段文字变化会制造假页面。旧式程序还可能把模块窗口预先创建为隐藏 `WTWindow`，清理阻塞弹窗时只能关闭确认过的消息框/文件对话框，不得把隐藏模块当残留窗口销毁；否则随后入口会报“指定窗口尚未载入”。

递归探针还必须实行进程归属白名单：启动前记录已有参考程序窗口，后续只点击、取消或关闭本次隔离进程及其明确 owner 链上的 HWND。桌面上“新出现的窗口”不能视为参考程序后代；全局前台窗口最多作为只读诊断信息，绝不能因此发送点击或关闭消息。失败运行生成的控件快照应由会话级 `validated=false` 隔离，报告器必须拒绝把它们回灌功能分母。上下文菜单的存在、菜单项命令处理器的执行和执行后状态是三个不同证据层：弹出菜单时序不稳定时，可先从已验证菜单读取命令 ID，再在隔离副本中调用同一窗口的命令处理器；只有捕获到同进程后代窗口、页面状态变化或可解释文件差分，才登记执行结果。

功能分母的窗口身份必须剔除数据载荷。若参考工具把 ROM 路径、工程名、当前记录名或测试文件名拼进标题栏，应先规范化为稳定窗口类型，再以控件类、控件 ID、树路径和动作建立身份；原始标题和来源快照仍作为观测元数据保留。否则每运行一个隔离样本都会凭空复制整窗动作，分母随证据次数增长，完成率失去意义。必须用“两个不同输入路径、同一控件树只产生一组动作且聚合两份来源”的单元测试锁定该规则；未载入与已载入确有不同结构时，可以保留为两个状态，但不能按文件路径拆分。

控件树同样不能把模板 HWND 当作可执行入口。旧式 MFC/Easy-Language 页面会同时保留当前页、其他页和设计期占位控件，其中一部分永久隐藏、尺寸为零或固定禁用。它们仍要进入显隐/启用状态集合，用于生成“寻找触发条件”的任务；但只有同一稳定控件在至少一份有效快照中同时 `visible=true`、`enabled=true`，才允许生成左键、右键、键盘或拖拽动作。必须用永久隐藏、永久禁用、隐藏后变可见三类单元测试锁定，避免把不可达模板计入分母，也不能因此漏掉条件入口。

上下文菜单发现文件只有在所属页签第二阶段签名全部匹配时才能回灌动作分母。输入框由 Windows 提供的撤销、剪切、Unicode 控制字符菜单与产品自定义菜单应分层统计：平台菜单按来源控件记录“入口已观察”，其可达性由该控件的右键与键盘快捷键动作验证，不把随系统语言/输入法变化的每条命令扩成产品功能；自定义命令则必须逐项进入分母、映射新版业务动作并验证结果。

带自然语言选择器的指令不能只凭控件项数推断底层编码。应在隔离 ROM 上选择一个非默认项，完成参数窗确定、父窗口确定和主窗口真实保存，再以资源解码器比较保存前后逻辑记录。参考工具可能同时进行指针拆分、池重排和内部跳转重定位，整 ROM 差异数不能直接等同于该指令的字段数；只有从语义差分中分离出的新增指令字节、固定字节和选项值，才能用于产品默认值、隐藏字段与自然语言下拉框。

## 递归前沿闭合后的证据规则

参考工具的递归分母必须同时保存“发现来源”和“执行来源”。动态按钮文字、当前记录名或文件路径会改变时，允许建立稳定身份别名，但只能由同一控件类、控件 ID、规范树路径和业务命令的双份有效证据推出，并记录两份源文件哈希；仅凭相似文字不得合并。系统文件框会在下拉展开、Shell 视图重建或导航后替换子 HWND，因此执行器应在每次动作前按规范路径重新解析控件，并把初始身份与重建后的状态分开记录。

递归前沿 `closed=true` 的语义仅是：所有有效快照生成的稳定动作都有有效旧版执行记录，且待办为零。它不能自动证明新版映射正确，也不能替代 ROM 字节黄金、取消回滚、保存重开或正式封装测试。产品放行仍需四层证据同时成立：参考动作闭合、新版动作回归、资源保存差分、正式 EXE 哈希和自检门禁。本轮最终参考分母为 3376/3376；无效会话、旧进程崩溃后产生的残留窗口以及没有稳定动作 ID 的叙述记录均被报告器拒绝。
## 2026-09-29：动态子窗口与复合指令边界取证

- 不能用参数窗截图推断保存字节。对于“确定”后同步弹出条件确认的旧程序，自动化必须异步触发父按钮，再按同进程/owner 链捕获新模态窗口；同步 `BM_CLICK` 会阻塞在消息循环内，导致探针误判父窗无法关闭。
- 同一条自然语言效果不一定是一条底层指令，反之亦然。必须以独立 ROM 的保存前后差分和重开解码确定边界；本轮证明“创建对象”和“对象运行规律”是相邻的两条记录，若编辑器为了界面方便把它们合并，会破坏插入、删除、循环目标和后续指令解析。
- 带绝对跳转的命名编号应在界面中保留参考工具的逻辑编号，同时在草稿层解析为已证明的指令边界地址；重排时只迁移能在旧/新边界映射中找到的目标。删除目标或目标不唯一时整次拒绝，不能把下拉编号直接当作裸地址写入。
- 对命名下拉的项目数、起始值、十六进制显示和条件分支分别取证。固定字节应隐藏但由保存黄金约束，条件确认应显式呈现；不能用通用数值框替代参考工具的命名资源选择。

## 2026-09-29：执行证据必须回填稳定动作身份

- 递归发现报告可以在已通过会话级 `validated=true` 门禁的证据文件中携带 `execution_records`，但每条执行记录必须引用由窗口状态、控件树路径、控件身份和动作类型共同生成的稳定 `action_id`。报告器按动作 ID 合并证据；窗口标题相同、按钮文字相同或同一次运行出现过都不能替代精确映射。
- 取消语义必须沿完整事务层级验证。参数窗关闭、父选择器恢复、数据库外层取消和主窗口真实保存应连续执行，最后比较隔离 ROM 的完整哈希或字节差分；只验证子窗关闭会遗漏父草稿、共享池重排或撤销栈污染。
- 候选分母随新快照、动态窗口和菜单持续增长是正常结果。已通过数量与待验证数量必须同时报告；只有被稳定动作 ID 命中的有效执行证据才能从 `pending` 迁移到 `passed`，失败会话和无 ID 的叙述性记录不得自动关闭动作。
- 旧式界面可能把分组框、静态标题、复合按钮和真正按钮全部暴露为同一 Win32 `Button` 类。一次中心点击无效果只能说明该坐标无可见结果，不能据此删除控件：应结合文字布局把“复制/完整/代码”等复合区域分点点击，并对会改变行内编辑框的坐标按钮保存前后控件状态。会打开模拟器、拼图或预览的按钮还要递归枚举其子窗口；产生错误框的边界按钮应在合法参数状态下再次测试，不能把一次错误提示当作功能无效。

目录链接的多表数据不能按当前表尾或相邻指针误判为多个固定池。应先对每个目录入口、首记录指针、末记录结束位置和物理固定边界建图，再分别让前、中、后表增长 1 字节并保存整 ROM 黄金：如果前表增长导致后续目录入口、指针表和正文整体后移，就应实现为一个有明确存储顺序的共享池。写回必须由活动 ROM 的目录动态求出各表位置，在单事务中重建正文、同表后续指针及后续表目录/指针；容量以最早表起点到已验证固定代码边界计算，不能把初始空隙分别重复承诺给每张表。相同物理指针只证明当前存储去重，不能据此决定编辑语义；必须另选已知别名记录做单项保存黄金，确认参考程序是联动原地改写还是写时复制后再开放。

结束码插入也不能一律复用“重排后只保留可达指令”的通用序列编辑。旧版武器动画在共享记录首行/中间行插入 `FF` 的黄金证明，它会为当前逻辑 ID 在原指针处插入一份带结束码的私有物理分配，同时保留结束码后的不可达原字节，再把原共享记录和后续池整体后移；其他别名仍指向搬移后的原记录，活动 `FE` 绝对循环目标随之重定位。原本独立的记录采用另一分支：只在所选指令边界插入 1 B，记录前缀留在原位，后缀和后续池后移 1 B。此类保存必须有按别名状态分支的专用补丁，并以整 ROM 哈希、别名语义、撤销和重做四重证据验收，不能只看当前项解码后显示为 `FF`。敌我双方、共享/独立、首/中/末位置和已有结束符无操作应汇总为可重复生成的矩阵证据；矩阵只能关闭实跑过的列表“插入”和 FF 左键动作，不得顺带把键盘触发、按钮右键或未发现的条件入口标为通过。

同一控件的左键、键盘激活和右键属于三个动作，必须分别采集。对于命令目录，可在一个隔离事务中让每个按钮获得真实键盘焦点后发送空格，核对新窗口标题并取消返回；右键则核对选择器 HWND、顶层窗口集合和草稿均未变化。最后还要取消外层数据库并调用真实保存确认 ROM 零差分。只有同时满足可见状态与最终字节门禁，才能把对应稳定动作 ID 从 `pending` 移到 `passed`。

上下文菜单还必须按有状态序列验证：复制后的粘贴、复制全部后的跨记录粘贴全部、粘贴后再剪切，以及删除后清空都依赖前一步状态。控件若是固定 200 行的 owner-drawn ListBox，`LB_GETCOUNT` 不能代表有效指令数；应截取列表区域并以动作前后图像哈希证明可见状态变化，同时用外层取消后的 ROM 零差分证明事务回滚。该证据足以关闭“动作可达与状态链”项，但不能证明保存布局；变长结构命令仍需逐项执行确定、主窗口真实保存、解码语义和整 ROM 差异黄金。

武器动画的确定保存黄金进一步证明，旧版数据库会按逻辑武器编号顺序重新序列化敌/我动画池，并用完整脚本字节作为去重键，而不是按旧物理指针维持别名。统一写回器必须因此同时满足：编辑共享项只为当前逻辑项写入新正文；未编辑别名保留原正文；内容相同的粘贴全部或清空结果共用同一新指针；池缩短后将被释放的旧尾部清零；所有活动 `FE` 目标按已证明指令边界重定位。普通粘贴的旧版语义是替换当前可见指令组，还要消费紧随其后的隐藏附属指令，不能与“插入”共用同一列表切片逻辑。该算法须由剪切、粘贴、粘贴全部、删除、清空五类整 ROM 哈希共同约束，不能为每个按钮分别硬编码差分。

图形拼图不能停留在“能够解码并显示”。若参考窗口允许图块级编辑，子窗口必须返回明确的领域草稿，由外层资源池事务统一做容量、指针、取消和撤销；不能让子窗口直接写工程，也不能让“确定”只关闭窗口。紧凑脚本往往存在多种等价编码，编辑器应选择一个确定性的规范化编码：显式记录下一图块及相邻坐标差，完整保留图块顺序、坐标、调色板和翻转位，并对位移值域、结束码及结束码后多余字节做校验。测试至少覆盖解码→规范化编码→再解码的语义等价、子窗取消零变化、子窗确定进入父草稿、父窗取消零写入及父窗确定后的共享池重排。

## 2026-09-30 武器拼图编码补充

- “语义等价的统一编码”不能自动替代参考修改器的写回格式。物理武器拼图沿用运行时解释器，但参考编辑器会为每个相邻图块选择最短转移：图块递增/保持/显式指定，以及 `X+8`、仅 X、`Y+8` 或 X/Y 双位移。实现应保留独立的旧版紧凑编码器，并用保存黄金验证整 ROM，而不能只做解码后画面相同的测试。
- 整图镜像的参考轴是规律原点，不是当前图块包围盒中心；水平镜像执行 `x=-x` 并切换 `$40`，垂直镜像执行 `y=-y` 并切换 `$80`。单块右键翻转应原位切换命令属性位，避免无必要重排。
- 光束拼图虽然与物理拼图具有相似画布，保存结果已证明不是可直接共用的安全写回协议。两者 codec 必须分离；在光束专用格式闭合前，不以物理 codec 的往返成功代替光束保存验收。
- “无操作确定”本身也是保存黄金：探针应按用例声明期望差分，编辑用例要求非零差分，无操作用例则要求保存前后完整哈希相同。不能用统一的“必须有差分”校验器把零差分保持错误地判为失败。
- 对尚未解析完的压缩语言采用能力分层：已经由受控保存和独立资料共同证明的直接图块、相对位移、行宽、重复及连续序列可以进入专用紧凑编码器；只知道参数宽度、尚不知道展开规则的控制码仍只能解析边界并标成只读。紧凑编码器必须在写入前执行“编码→再解码→坐标/顺序/图块逐项相等”，并在全记录集上统计最大增长与共享池余量。无操作确认应保留原始字节，不为格式整齐而重编码；语义回环通过也不能冒充参考工具的规范化字节已逐字节闭合，后者仍需独立保存黄金。
- “隐藏前缀”不能只建模为固定字节数。若参考页把可选首部控制和末尾控制分别投影到复选框/坐标框，领域模型应提供可逆的 `split/join`：正文编辑只替换正文，坐标控件只增删或修改对应控制，完整记录模式仍显示原始流。必须用“仅首部、仅尾部、两者都有、两者都无”至少四类记录验证无损往返；否则对共享尾记录固定裁掉 N 字节会悄悄删掉真实绘图命令。

## 2026-09-30 有状态工具的操作链取证

- 模拟器、录制器和向导式工具必须按“前置状态—动作—提示—画布输入—后续动作—结果”取证，不能把控件表当作可任意排序的按钮集合。本轮旧版运动规律模拟器证明，正确顺序是首次开始→确认提示→画布创建物体→再次开始→移动或鼠标记录→结束；在创建之前调用移动只会得到“请先点击开始”，并不证明移动按钮无效。
- 模态提示的控件 ID 不能按通用习惯猜测。旧程序的“确定”按钮使用了 ID 2；若通用弹窗清理器按 IDCANCEL 优先，会表面关闭提示、实质取消状态迁移。探针应优先按可见文字与 owner 链选择业务按钮，并在下一状态验证结果。
- 旧式界面可能先更新内部文本、后刷新跨进程可见值。动态验收应等待稳定状态，并从同一次有效窗口快照读取最终值；过早读取到空串不能覆盖随后已显示的 `00`。执行证据只有在操作结果、检查状态和 ROM 零差分同时成立时，才回填稳定 `action_id`。
- 参考程序要求提权时，优先在隔离副本上以 `RunAsInvoker` 让探针和目标处于同一完整性级别；不能借权限失败降低门禁。对仍只接受桌面辅助功能输入、拒绝进程内 UIA/SendInput 的控件，要把人工桌面复验与自动状态链证据分开记录，不得伪造字段写入成功。
