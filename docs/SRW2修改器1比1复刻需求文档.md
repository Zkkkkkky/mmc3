## 1. 文档目的与范围

### 1.1 撰写背景

用户要求对参考产品 `SRW2_patched.exe`（旧版《第二次机器人大战》修改器，易语言编写）进行 1:1 复刻。此前多版实现均未达到用户预期，其根本原因经前期四项研究（任务 1—5）复盘确认：

1. **黄金对照系统性缺失**：从未建立"参考 EXE 单字段修改 → 保存 → 二进制差分 → 重开验证"的闭环对照流程，导致每版实现只在"界面像"而非"字节对"的层面收敛。19 个功能区域中仅"其他全局参数"1 项达到已对齐状态（见 `docs/research/legacy-modifier/SRW2一比一复刻差异矩阵.md`）。
2. **按不完整理解反复实现**：缺少一份以第一手证据为基准、精确到控件与字段的需求文档，各版本实现者对同一功能的理解各自漂移。
3. **数据字段语义未确认**：大量 ROM 字段停留在 candidate 级证据，"未验证不写入"的保守策略造成至少 15 处按钮禁用（见 `docs/DC修改器使用说明.md`）。
4. **ROM 容量硬约束未解决**：人物属性池 477 字节、头像池 497 字节已占满，事件区约 8 KiB；当前受支持 ROM 已由 `C9 62`、99 项经验和 50 字节成长记录确认为 99 级，超过 99 级仍缺重排协议。旧 `audit.nes` 的 60→61/3778 字节重排属于不兼容布局，不能作为当前 ROM 的扩容算法。

本文档的目的就是终结上述循环：把已核实的第一手证据固化为可追踪的需求条目（REQ 编号），把未核实内容显式标注为待验证，把参考版**没有**的行为固化为否定证据，使后续开发不再"猜"。

### 1.2 文档地位

- 本文档是 1:1 复刻的唯一需求基准；实现与本文档冲突时，先复核证据，再修订本文档，禁止实现侧自行偏离。
- 本文档自身以证据分级为原则写作：凡引用 `output/verification/legacy-ui-probe/`（探针第一手产物）与 `tools/audit_legacy_*.py`（差分审计脚本）的结论为**已证实**；凡标注“推断待验证”的内容必须在实现前补做黄金对照；凡标注“否定证据”的内容**禁止复刻**。
- 需求已按模块拆分至 `docs/需求拆分/`（README + M00—M18）：模块文档为工作分解与逐模块验收单元；两者冲突时以本文档为准，第 11 章统计口径不变（v1.2，2026-09-14）。

### 1.3 范围界定：1:1 指什么

1:1 复刻指以下三层同时逐项对齐：

| 层         | 含义                                                | 判定方式                                 |
| --------- | ------------------------------------------------- | ------------------------------------ |
| L1 界面布局   | 窗口集合、窗口标题、控件清单（类名/控件 ID/文本/相对布局）、页签结构、列表条目格式      | 与控件树枚举（`controls_summary.md`）及截图逐项比对 |
| L2 操作动线   | 菜单/快捷键/按钮触发顺序、窗口打开与关闭方式、页签切换方式、"确定→缓冲、保存→落盘"的保存模型 | 与探针动线记录及操作动线规格逐项签核                   |
| L3 数据写入行为 | 每个可编辑字段写入 ROM 的确切偏移、字节宽度、字节序、取值范围、显示换算            | 黄金对照四步闭环（见第 3.1 节）                   |

不在 1:1 范围内（视为超集或明确排除）：

- 参考版的运行时 bug（如"更改倍数"触发易语言运行时错误）——如实记录，不复刻其错误行为（见 4.17）。
- 参考版保存时的文本 Token 归一化副作用（6 个偏移）——必须显式排除（见 6.3）。
- 当前新修改器已有的工程化能力（.dcmod 工程、撤销重做、事务回滚、派生 ROM 输出等）——定位为超集能力，依 D1 决策（2026-09-14）**保留且不做隐藏**；保留不得改变参考版已有功能的控件清单、操作动线与字节输出（见第 7.3 节）。

### 1.4 读者与使用方式

- 实现者：按第 4—6 章条目逐项实现，每项完成后按第 10 章验收判据自验。
- 验收者：按第 10 章总量化完成定义判定模块是否"已对齐"，替代旧的五级状态口径。

### 2.2 运行形态

参考产品为单进程两阶段形态：

1. **启动器阶段**：显示作者署名 `断月残心` 与"进入修改器"按钮。本产品启动器为精简自定义布局，不参考截图、不含外部链接按钮、不含 QQ/QQ 群信息（依 2026-09-14 决策；参考版原含 4 链接与 QQ 群，已不复刻）。
2. **主窗口阶段**：点击"进入修改器"后启动器窗口销毁（HWND 失效，探针需重新枚举窗口），出现带菜单栏的主窗口。未载入 ROM 时菜单仅"文件(F)"与"帮助(H)"；打开 ROM（通用"打开"文件对话框）后出现"数据(A)"菜单、窗口标题追加 ROM 路径、主窗口中央区域可用。

所有次级功能窗口（数据库/文字库/地图动画/文字转换/剧情事件/导出机体/属性计算器/存档编辑器/其他）均由"数据(A)"菜单或快捷键打开，为模态子窗口。

## 3. 复刻总原则与验收总纲

### 3.1 黄金对照流水线（第一需求）

**REQ-GOLDEN-001**：黄金对照流水线是本项目第一需求，优先级高于一切界面与功能开发。其四步闭环为：

1. **复制**：复制基准 ROM 得到 `before.nes`，再复制一份 `after.nes` 供参考 EXE 编辑。
2. **单字段修改**：以自动化（pywinauto，参照 `tools/audit_legacy_modifier_ui.py` 的参数化驱动方式）驱动参考 EXE，对目标控件做单一字段修改，点"确定"提交到缓冲，再"文件→保存"落盘。
3. **二进制差分**：对 `before.nes` 与 `after.nes` 做全字节差分，记录所有变化偏移；除已知归一化副作用偏移（见 6.3）外，变化集必须能被"该字段的预期偏移"完全解释。
4. **重开验证**：以全新进程重新打开 `after.nes`，读取同一控件显示值，必须等于第 2 步请求写入的值。

**REQ-GOLDEN-002**：黄金对照必须逐字段执行，禁止"改一批字段看一次差分"的混合用例作为对齐依据；混合用例仅可作为回归。

**REQ-GOLDEN-003**：当前新修改器的每个可写字段在宣称"已对齐"前，必须有对应的黄金对照用例与结果存档（建议存于 `output/build/legacy-diff-audit/`，与现有审计脚本产物目录一致）。

### 3.2 量化验收指标

| 指标          | 定义                                                  | 总目标             |
| ----------- | --------------------------------------------------- | --------------- |
| G1 黄金对照覆盖率  | 已通过黄金对照的字段数 / 参考版全部可编辑字段数                           | ≥ 95%           |
| G2 逐字段差分通过率 | 差分变化集可被预期偏移解释的用例比例                                  | 100%（不允许未知偏移漂移） |
| G3 禁用解禁数    | 新修改器中因"未验证"而禁用的控件数从 ≥15 降为 0（或逐项给出不可解禁的容量/安全性理由）    | 0               |

### 3.3 "已对齐"的严格定义

一个功能模块宣称"已对齐"，必须同时满足：

1. L1 界面布局与控件树枚举逐项一致（控件 ID 可映射，允许 UI 框架差异但信息结构不得增删）；
2. L2 操作动线与探针动线记录一致（触发方式、窗口层级、保存模型）；
3. L3 该模块全部可编辑字段通过黄金对照四步闭环；
4. 参考版不存在的增强功能依 D1 决策（2026-09-14）保留为超集能力，不构成 1:1 偏差；判定"已对齐"时黄金对照差分范围仅限参考版存在的功能行为（见第 9 章）。

### 3.4 三类内容的写作与实现纪律

| 类别     | 标注                  | 实现纪律                                                              |
| ------ | ------------------- | ----------------------------------------------------------------- |
| 参考版已证实 | （默认，附证据路径）          | 必须实现且逐项对齐                                                         |

## 6. 行为需求

### 6.1 保存模型（两级提交）

参考版保存模型（操作动线规格 + 审计脚本实测流程共同证实）：

1. **编辑草稿层**：子窗口（数据库/文字库/地图动画/剧情事件/其他/存档编辑器）内的一切修改，在点"确定"前均为草稿。
2. **提交缓冲层**：点子窗口"确定"把整窗修改提交到内存中的 ROM 缓冲区（此时尚未落盘）；点"取消"丢弃草稿并关闭窗口。
3. **落盘层**：仅主窗口"文件→保存（Ctrl+S）"把缓冲区写回 ROM 文件；**直接覆盖原文件，无确认对话框**。
4. **例外**：文字库窗口只有"确定"（无取消）；文字转换与属性计算器无确定/取消（即时工具，不产生修改）；存档编辑器自带独立四阶段（打开→读取→写入→保存，见 4.14）。
- REQ-BEH-001：两级提交模型逐项实现；"取消"必须真正丢弃（参考版无"取消也落盘"行为）。
- REQ-BEH-002：保存直接写回原文件，无确认弹窗、无备份；保存后继续编辑无需重开；重开后显示值必须等于已保存值（黄金对照第 4 步的语义）。
- REQ-BEH-003：子窗口间切换不触发保存（各自独立提交）。
- REQ-BEH-004：无自动保存、无崩溃恢复【否定证据 NEG-2/NEG-3】。
- REQ-BEH-SUPER-001：依 D1 决策（2026-09-14），当前新修改器的超集安全行为（关闭脏窗口的未保存询问、保存为派生 ROM 而非原地覆盖、覆盖前时间戳备份）保留，不构成 1:1 偏差；本节 REQ-BEH-001~004 描述的是参考版行为基线，用于黄金对照差分范围判定，不作为移除超集安全行为的依据。
