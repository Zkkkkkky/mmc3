# 机体碎片与物理武器图库解绑定：论证、实施与验证方案

> **文档状态：方案已完整记录，尚未实施。** 记录日期：2026-09-10。C1 是当前首选候选路线，仍须通过阶段 0 的证据门和阶段 2 的全局装箱/容量门后才能定案。
>
> 本文只定义技术路线、执行顺序、验证门槛和回退办法，不表示当前修改器已经支持图库解绑定。当前界面中的机体碎片、图像地址和地图动画写入仍应保持禁用或只读；在实际实现这些功能的同一变更中，必须同步更新 `docs/DC修改器使用说明.md`。

## 1. 决策摘要

本文所称“物理武器”是旧资料中的“精灵武器”：即通过 `42 69` / `C2 69` 路径，从精灵图块组成动画的武器。它不包括使用 `F2 03 01 XX` 动态选择背景图库的背景武器。

现有绑定不是修改器界面人为设置的限制，而是当前战斗绘图链路的实际约束：`42 69` / `C2 69` 不携带独立图库号，物理武器继承参战机体碎片所在的精灵 CHR 页。机体碎片和物理武器又可能在同一帧出现，因此只增加一个“武器图库”下拉框并直接切换 CHR Bank，会把同一槽中的机体碎片一并切走，造成花图、缺图或错误取图。

首选方案是实现**编辑层逻辑解绑定、构建期全局静态链接、运行时保持原机制**：

1. 修改器分别管理机体碎片资产和物理武器图形资产，用户不再手工把二者贴进同一图库。
2. 构建器计算每个机体的“碎片 + 所有可达物理武器/公共精灵特效”共驻闭包，把闭包自动装入固定的 2 KiB 运行页；多个闭包兼容时可共享页面，并按内容去重。
3. 构建器把生成页的 Bank 写入机体战斗外观记录；运行时仍由 `42 69` / `C2 69` 继承该页，不增加战斗期切换。这相当于把原来依靠人工完成的共图库布局改为链接器自动完成。
4. 只有单机体共驻闭包装不下、或全局共享武器的本地图块号约束无解时，才升级为“机体×实际武器”攻击期组合页，并增加查表、切换与恢复。
5. 未启用独立武器资产的旧工程继续走原路径，目标是生成结果逐字节不变。

这个方案取消的是制作和资源管理上的绑定，不取消 NES 的硬件上限。每个运行页仍只有 2 KiB，即 128 个 8×8 图块；同屏 64 个精灵和每扫描线 8 个精灵的限制也仍然存在。

静态链接能否覆盖全部机体，取决于单机体共驻闭包大小、共享武器的本地图块号约束，以及有效 CHR 中可证明可重排或可分配的页数。攻击期组合页是第二级方案；若其容量审计仍不通过，才研究 Mapper 194 的 CHR-RAM 动态上传。不得未经验证改用 Mapper 199，也不得把当前 464 KiB 的 PRG 托管空间误当作 CHR 空间。

## 2. 基线、术语和范围

### 2.1 当前基线

| 项目 | 当前事实 |
|---|---|
| 推荐编辑基线 | `output/rom/DC_kuorong_464K.nes` |
| Mapper | 194 |
| PRG | 1 MiB，其中托管空闲区合计 464 KiB |
| CHR | 256 KiB，当前推荐构建保持源 CHR 逐字节不变 |
| 只读源 ROM | `references/rom/source/新DC.nes` |
| 旧兼容基线 | `references/rom/baselines/DC_kuorong.nes` |
| 必选运行验证器 | Mesen 0.9.9；FCEUX 2.6.6 不作为该 1 MiB Mapper 194 ROM 的验收依据 |

精确文件大小、哈希、Bank 布局和模拟器边界以 `docs/交接文档.md` 为准。实施期间不得覆盖两个 `references/rom/` 输入文件，所有派生 ROM、IPS、报告和模拟器证据必须写入 `output/` 对应目录。

必须区分三种“兼容”：

1. **旧工程兼容**：旧 `.dcmod` 没有新字段时按“继承机体碎片图库”迁移。
2. **旧 ROM 可读兼容**：修改器仍可按现有能力打开已认证旧基线，但不因此自动获得新功能写入资格。
3. **新功能可写 profile**：只有 Gate 0 明确记录地址、CHR 所有权、保护签名和完整验证计划的 ROM profile 才能写入解绑定数据。

第一版默认只把推荐 464 KiB 扩容基线作为“新功能可写”的候选；旧兼容基线先保持可读但新功能只读，除非 Gate 0 为它单独完成取证并建立独立 profile。最终完成定义必须按每个声明支持的 profile 分别验收，不能用推荐基线的结果替代旧基线。

### 2.2 术语

| 术语 | 本文定义 |
|---|---|
| 图块 | 一个 8×8、2bpp 的 NES CHR 图块，16 字节 |
| 图库 | 旧资料常用单位，1 KiB，共 64 个图块 |
| 运行页/图库对 | MMC3 的一个 2 KiB 精灵 CHR 映射单位，共两个相邻图库、128 个图块 |
| 机体碎片 | 叠加在机体主体之上的战斗精灵部分及其拼图脚本，不是“ROM 碎片”或扩展资源块 |
| 物理武器/精灵武器 | 由 `42 69` / `C2 69` 调用组图规律并使用精灵图块显示的武器动画部分 |
| 背景武器 | 通过另一条动画路径显示、可见 `F2 03 01 XX` 图库切换的背景动画；不属于本次解绑定对象 |
| 逻辑解绑定 | 工程和编辑器分别保存碎片与武器资产，用户无需安排二者物理同页 |
| 物理解绑定 | 运行时两套资产各自独立映射且无需合成或复制；这需要额外 CHR 槽或 CHR-RAM 上传 |

现有 64 KiB 机体扩展会把“主体拼图脚本池”和“碎片拼图脚本池”放到不同 PRG Bank Pair。它解决的是 PROM/PRG 中脚本存储容量，不是 PPU 使用的 CHR 图库绑定，不能视为本功能的已有实现。

### 2.3 目标

- 在工程模型中独立导入、预览、复用和导出机体碎片资产与物理武器图形资产。
- 同一物理武器资产可以安全复用于碎片图库不同的多个机体，不要求用户手工复制贴图。
- 保持原 `42 69` / `C2 69` 敌我取图语义、动画节奏、调色板和移动规律。
- 构建器在写 ROM 前确定性地完成依赖闭包、占用分析、重映射、装箱、去重和容量校验。
- 首选路线不增加战斗期 CHR 切换；若进入攻击期组合页路线，则所有正常和异常退出路径都必须恢复原 CHR 映射。
- 旧工程和未启用解绑定的编辑流程保持兼容；旧 ROM 继续遵守既有可读能力，但新功能写入只对 Gate 0 明确认证的 profile 开放。错误必须在生成正式 ROM/IPS 前失败。

### 2.4 非目标

- 不借此功能突破 NES 的 64 精灵、每扫描线 8 精灵或 128 图块运行页上限。
- 第一版不改造背景武器路径，不重写全部战斗动画系统。
- 第一版不更换 Mapper，不以 Mapper 199 作为捷径。
- 第一版不承诺无限数量的机体×武器组合；容量不足时必须报告并停止。
- 不根据“页面全零”直接认定 CHR 可写，也不把历史资料中的地址未经验证写进构建器。

## 3. 论证与证据链

### 3.1 已确认事实

| 证据 | 结论 | 对方案的含义 |
|---|---|---|
| `references/research/fc资料集-v1.16/武器动画标志代码.htm` | `42 69 + AA BB CC DD` 从“机体碎片模块”取物理武器组图；`C2 69` 主要改变敌我方的 `00-7F` / `80-FF` 取图侧 | 原指令没有独立图库参数 |
| `references/research/fc资料集-v1.16/page_1188.html` | 示例“冲击波”贴图与盖塔龙碎片在同一图库 | 共图库是原资源制作流程的一部分 |
| `references/research/fc资料集-v1.16/page_849.html` | Mapper 4/74/194 的既有切页方式要求相邻两个精灵图库成组考虑，碎片和精灵武器图像被共同规划 | 直接切走一个运行页会影响共享该页的所有精灵图块 |
| `references/research/fc资料集-v1.16/page_1191.html` | 头像正片、双方机体碎片和物理武器共同消耗 OAM；同屏 64 精灵、每扫描线 8 精灵 | 解绑定不能解决精灵数量和扫描线闪烁 |
| `src/fc_editor/codecs/event.py` | 当前结构解码把 `F2` 识别为 `$EBF0` 的“批量切换映射”，长度为 `3 + count` | ROM 已有写 CHR 映射影子的机制，但存在切换能力不等于可同时驻留 |
| 当前基线 ROM 的只读反汇编检查 | Bank `$04` 的 CPU `$8E80/$8ED1` 将战斗外观记录 byte `+7` 写入 `$04D0/$04D1`；Bank `$1C` 的 `$9295-$9298` 再把相应值送入 `$04D8` 起的 CHR Bank 影子，相关例程最终写入 MMC3 `$8000/$8001` | 首选路线可继续使用外观记录选择静态生成页；精确分支仍须在实施前固化为测试 |
| `src/fc_editor/expansion_unit.py` | 机体战斗外观目前以 10 字节不透明记录无损搬运；主体和碎片脚本可在 PRG 中分池 | 在开放编辑前还需建立逐字段语义和 lossless codec |
| `src/dc_modifier/legacy_windows.py` 与 `src/dc_modifier/legacy_tools.py` | 碎片上传、图像地址和动画编辑仍禁用或只读 | 当前产品尚无可安全承载该功能的编辑入口 |
| `docs/交接文档.md` | 当前扩容只增加 PRG；有效 CHR 仍为 256 KiB，Mapper 199 实验曾造成画面损坏 | PRG 空间可保存表、脚本和源图数据，但不能直接充当 PPU 图块页 |

历史资料只作为逆向线索。上表中涉及 ROM 地址、Bank 值和分支条件的结论，在实施第 0 阶段必须针对当前推荐基线重新生成反汇编与 Mesen 追踪证据，并固化为测试，不能只凭 HTML 说明直接修改 ROM。

### 3.2 当前绑定链路

当前行为可概括为：

1. 战斗配置装载双方机体外观数据，其中包含碎片使用的 CHR Bank 信息。
2. 该信息进入 `$04D8-$04DD` 一带的 CHR 映射影子，并由 Mapper 写入例程提交到 `$8000/$8001`。
3. 物理武器脚本执行 `42 69` 或 `C2 69` 时，只给出组图规律、横向规律、纵向规律和等待时间；它根据敌我方及图块高位选择 `00-7F` 或 `80-FF` 区间，没有自己的图库号。
4. 机体碎片与物理武器因此从同一侧已经映射的 2 KiB 运行页取图，而且两者可能同帧显示。
5. 若在物理武器出现时把该槽直接换成另一页，武器可能正确，但仍在屏幕上的机体碎片会从新页的同编号位置取图，从而损坏。

因此，“增加图库字段 + 在动画开始时执行一次 F2”不是完整解法。任何可接受方案都必须满足**同时驻留**或**等价合成**；只要引入战斗期切换，就必须覆盖全部恢复路径。

### 3.3 容量现实

- 一个运行页只有 2 KiB，即 128 个图块。合成后所有被引用的碎片图块、物理武器图块及已确认的保留位置必须装得下。
- 当前 CHR 总量仍是 256 KiB。当前基线的只读字节扫描只能得到“24 个全零 1 KiB 候选页、其中 10 个偶数对齐的全零 2 KiB 候选对”：`00-01`、`AE-AF`、`B2-B3`、`B4-B5`、`B6-B7`、`B8-B9`、`BA-BB`、`BC-BD`、`BE-BF`、`E8-E9`。全零页仍可能是故意映射的空白页、清屏页或保留页；这 10 对目前全部属于 `unproven`，只有静态引用扫描与运行时追踪都证明未使用后，才能转为 `allocatable`。
- 静态链接应优先重排已经证明属于碎片/物理武器的现有页，复用原容量；不能把所有组合都简单追加为新页。若升级为攻击期组合页，最坏情况下才会出现按“碎片页内容 + 武器资产 + 槽位语义”增长的组合数，必须用内容哈希去重并在实现前做全局容量报告。
- 464 KiB 托管空闲空间属于 PRG。它适合保存映射表、重定位脚本、组合元数据或供 CHR-RAM 上传的源数据，但 PPU 不能把它当作 CHR-ROM 页直接取图。

## 4. 方案比较与选择

| 方案 | 能否解除制作绑定 | 优点 | 主要问题 | 决策 |
|---|---:|---|---|---|
| A. 只加“物理武器图库”字段并直接换 Bank | 否 | 改动小，容易做出看似有效的演示 | 同槽机体碎片会被切走；退出恢复、敌我槽位和共享脚本仍未解决 | 否决，最多用于证明切页指令可用 |
| B. 永久保留一个独立 2 KiB 精灵槽给武器 | 有条件 | 运行时无需复制组合页 | 现有两侧机体、头像、大型机及其他对象可能已占用槽位；目前没有“所有战斗模式都空闲”的证据 | 仅作调查项；没有完整追踪不得采用 |
| C1. 构建期全局静态链接，每机体固定共驻页 | 是，逻辑层完全解绑定 | 运行时完全沿用原机制；无需新增查表、切换和恢复；可重排现有资源页 | 单机体的碎片与全部可达武器必须同页；共享武器在各页通常要保持同一本地图块号 | **第一优先** |
| C2. 按“机体×实际武器”生成攻击期组合页 | 是，逻辑层完全解绑定 | 只需让当前武器与碎片共驻，缓解单页闭包过大 | 增加 CHR 组合、运行时查表、切换与恢复，退出路径风险更高 | C1 无解后的升级路线 |
| D. 物理武器存 PRG，战斗时上传到 CHR-RAM | 是，且更接近物理解绑定 | 减少 CHR-ROM 组合复制，可利用扩展 PRG | 必须核清 Mapper 194 的混合 CHR-ROM/CHR-RAM 语义、上传窗口、带宽和渲染关闭时机；运行时风险高 | C2 容量门失败后的独立研究方案 |
| E. 更换 Mapper 或全面重做精灵调度 | 是 | 理论自由度最高 | 已有 Mapper 199 花屏先例；兼容性、烧录卡和固定 Bank 风险大 | 本项目当前边界内否决 |

生产路线的决策门如下：

1. 先完成 CHR 所有权清单、机体→武器可达图、共享脚本约束和静态链接 dry-run。
2. 若所有机体共驻闭包都能装入 2 KiB，且全局图块号约束有解，采用 C1；运行时不打补丁。
3. 若只有少数闭包超限或共享脚本约束无解，评估脚本安全复制/重定位；仍不能解决时，才进入 C2 的容量与运行时论证。
4. 若 C2 只够少量组合，第一版可明确限制最大组合数并提供容量诊断，但不得静默覆盖现有 CHR。
5. 若目标要求超过已认证 CHR 容量，则暂停产品实现，单独论证 D；不得自动改 Mapper。

## 5. 推荐架构

### 5.1 三层分离

**工程/编辑层**保存独立资产和语义关系：

- `FragmentGraphicAsset`：碎片 CHR 图块、碎片拼图脚本、调色板元数据、已用图块集合和来源信息。
- `PhysicalWeaponGraphicAsset`：物理武器 CHR 图块、组图规律、移动规律、调色板元数据、已用图块集合和来源信息。
- `PhysicalWeaponBinding`：武器或动画到图形资产的绑定模式。至少支持“继承机体碎片图库”和“独立资产”两种模式。
- 资产使用稳定 ID 和内容哈希；共享资产不因被多个机体引用而复制为多份工程数据。

这些名称是设计角色，不要求最终 Python 类必须使用完全相同的名字。正式编码前应先决定武器 ID、动画 ID、组图规律 ID 之间的真实主键关系。

**构建层**负责把逻辑资产转换为 ROM 可运行资源，优先完成静态链接：

- 解析碎片和物理武器脚本中的全部图块引用。
- 建立“机体→所有可达物理武器/公共特效”的共驻需求图，而不是只看机体的两个表面武器槽。
- 为共享物理武器分配跨页稳定的本地图块号，再把每个机体的碎片和完整依赖闭包装入 2 KiB 页；多个兼容闭包可共享一页。
- 只重写 codec 已明确识别的碎片或武器图块操作数；遇到未知、间接或自修改引用时失败，不猜测。
- 按运行页字节、重映射脚本和槽位语义进行内容寻址去重。
- 优先使用已经证明可重排的原碎片/物理武器页，再从显式的“已证明可分配 CHR 页”清单分配新增的相邻、偶数对齐页，并输出所有权和容量报告。
- 把生成页的偶数 CHR 基页写回相应机体战斗外观记录 offset `+7`；所有指针、Bank、长度和重叠关系在写 ROM 前断言。

**首选静态路线的运行层不新增行为**：

- 原装载器照常从战斗外观记录取得碎片 Bank。
- 原 `42 69` / `C2 69` 照常从同一运行页取碎片和物理武器。
- 因完整依赖闭包已在构建期共驻，攻击开始和结束时不需要切换或恢复。
- 这条路线不新增 PRG 查询表、动画 Hook 或固定 Bank 补丁。

**只有静态链接失败时，升级路线的运行层才选择和恢复**：

- 以 `(battle_appearance_id/unit_id, physical_animation_id)` 为内容查询键取得 C2 表项 `{chr_pair, optional_fragment_script_selector, optional_weapon_animation_or_composition_selector}`；最终采用外观 ID 还是机体 ID 由 Gate 0 的共享关系决定。敌我 side 只决定写 `$04D8` 还是 `$04D9`，不应无故复制相同内容表项。
- 在首次解析任何依赖该表项的脚本或图块前，保存目标槽当前 Bank、切到组合页并应用可选 selector；若选择顶层动画副本，不能等到第一个物理对象已经开始生成才处理。
- 同一动画重复调用 `42 69` / `C2 69` 时保持幂等，不反复破坏保存值。
- 组合页可保持到整段顶层攻击事务结束；恢复点必须由 Gate 0 证明，覆盖未命中/跳过、动画中止、反击切换、单位击毁和战斗场景退出。不能看到任意 `FF` 就恢复，因为顶层脚本、物理组图和子规律都可能含有 `FF`，且同一攻击可能有多个并发对象。
- 若存在并发或嵌套对象，使用显式 active-state 或引用计数，确保只在最后一个依赖对象结束后恢复；场景退出另设兜底清理，使遗漏分支不能污染下一场战斗。

升级路线究竟采用“扩展现有 VM 服务”“在物理武器入口挂钩”还是“生成前后置包装脚本”，必须由第 0 阶段的控制流追踪决定。优先选择可放在普通 PRG Bank 且固定 Bank 改动最小的方式；若必须修改受保护的 `$7E-$7F`，必须显式更新保护签名、Bank 差异断言、交接文档和模拟器证据，不能绕开现有保护测试。

### 5.2 静态链接与组合页打包规则

打包器必须遵循以下确定性规则：

1. 解码双方资源，得到每个实际引用图块及引用位置；同时枚举共享指针、别名、变形、剧情替换和公共特效等可达关系。
2. 为每个机体计算共驻闭包，并为同一物理武器在所有目标页分配相同的本地图块号。共享武器脚本是全局数据；若本地图块号不同，就必须有经过验证的脚本副本与选择机制，不能悄悄改写一份共享脚本。
3. 构建共驻约束图，把闭包兼容的多个机体分组装箱；同一图块内容可按哈希合并。装箱只针对实际可达关系，不生成机体和全部武器的笛卡尔积。
4. 先在已证明可重排的原资源页内求解；新增页只能来自显式认证清单。每个 2 KiB 基页必须为偶数，且 `base/base+1` 同时有合法所有权。
5. 重写已确认的碎片和武器图块操作数，并保留翻转、属性、相对坐标和帧序列等非图块位；重新解码后证明每个引用都指向预期像素内容。
6. 生成完整 2 KiB 页、机体 Bank 记录和链接报告；同样输入、不同遍历顺序都必须逐字节生成相同输出。
7. 静态闭包超过实际可用图块数、全局本地图块号约束无解、存在不可解码引用、没有合法页或 Bank 编码越界时，构建失败并列出具体机体、武器、脚本、图块数和冲突位置。
8. 只有明确记录 C1 无解原因后，才为实际可达的 `(battle_appearance_id/unit_id, physical_animation_id)` 生成稀疏 C2 表项 `{chr_pair, optional_fragment_script_selector, optional_weapon_animation_or_composition_selector}`。C2 页必须保持基础碎片及同半区公共资源的本地图块布局，除非表项也选择经过验证的碎片脚本副本；同理，武器必须使用跨组合页固定的本地图块号，或由表项同时选择经过验证的 per-combination 组图/动画脚本副本，并审计 8 位规律 ID 命名空间容量。

第一版应先比较两种静态重排策略：固定碎片、只移动武器的保守策略；以及同时重写已完全解析的碎片与武器引用的全局装箱策略。前者影响面更小，后者可能显著提高容量利用率。任何策略都必须由 lossless codec 和完整引用覆盖率决定，不能为了装得下而重写未知字节。

### 5.3 兼容与工程持久化

- 新字段默认值为“继承机体碎片图库”，与当前 ROM 行为完全一致。
- 若工程中不存在独立物理武器资产，构建器不重排/分配新页，也不安装运行时补丁，目标产物应与功能加入前的相同输入逐字节一致。
- 第一版明确以 `.dcmod` 为可续编的语义源。项目保存必须保留资产、绑定、内容哈希、来源和冲突处理决策。若现有操作模型不能无损表达这些语义，则升级 schema，并提供从旧版本单向迁移和未知新版本拒绝逻辑；迁移不得覆盖原工程，必须另存新文件或先创建可验证的恢复副本。
- `.dcunit` 若携带碎片或武器资产，清单必须声明依赖和哈希；导入共享武器资产时提供“按哈希复用、复制为新资产、取消”三种明确策略，禁止静默覆盖同 ID 不同内容的资产。
- 撤销/重做以一次资产或绑定操作为事务，必须同时恢复资源分配预览、组合数和容量诊断。
- 构建动作必须同时保存匹配的 `.dcmod` 工程副本。派生 ROM 内只要求保存经过认证的“已编译布局描述符”（格式版本、来源 profile、布局/资产哈希和已编译映射），不承诺仅凭 ROM 恢复编辑前的完整逻辑资产边界。
- 单独打开带该描述符的派生 ROM 时，修改器可以校验并展示已编译布局，但碎片/物理武器的语义编辑保持只读，并提示打开匹配 `.dcmod`；其他已验证的普通 ROM 字段仍按现有能力编辑。无修改直接另存必须逐字节一致。未来若要“只靠 ROM 完整反编译回逻辑资产”，需另立方案并为 ROM 内嵌完整源资产元数据，不混入第一版。

### 5.4 修改器交互草案

在所有 codec 和运行时验证通过前，现有控件继续只读。开放后建议提供：

- 机体页：“碎片资产”选择、导入、预览、已用图块和被引用机体列表。
- 武器页：“物理武器图形”选择及“继承碎片图库 / 独立资产”模式；背景武器显示为不同类别，避免混用。
- 组合预览：同时显示碎片层、武器层、冲突图块、预计运行页和敌我取图区间。
- 容量面板：逻辑资产数、去重后静态运行页数、可选 C2 组合页数、已分配/剩余 CHR、不能打包的闭包及原因。
- 保存前验证：任何红色冲突都会阻止 ROM/IPS 输出，而不是只给警告。

## 6. 分阶段执行方案

以下阶段必须按顺序推进。前一阶段的退出条件未满足时，不得以“界面已经能选”为由进入下一阶段。

这些阶段是技术放行门，不是把文档同步机械推迟到阶段 5/6 的许可。若各阶段以独立变更落地，则每次真正改变活动编辑器功能、界面、数据或工作流，都必须在同一变更中更新 `docs/DC修改器使用说明.md`；每次真正改变 ROM/CHR 布局、运行时行为、补丁点或正式哈希，也必须在同一变更中更新 `docs/交接文档.md`。只有所有阶段最终一次性合并时，才可在阶段 5/6 集中完成这些同步。

### 阶段 0：证据冻结与动态追踪

**工作内容**

1. 对推荐基线和旧兼容基线分别记录 iNES、PRG/CHR、Mapper、SHA-256，并冻结第一版的“可读 profile”和“新功能可写 profile”；每个可写 profile 独立记录补丁前置字节和验证矩阵。
2. 反汇编并标注：战斗外观 10 字节记录的全部字段，尤其是 offset `+7`；双方碎片 Bank 的装载路径；`$04D0/$04D1` 与 `$04D8/$04D9` 的真实职责；`$04D8-$04DD` 提交 `$8000/$8001` 的例程。
3. 追踪 `42 69`、`C2 69`、`F2` 处理器，区分顶层武器脚本、物理组图和子规律中的各级 `FF`，并找出未命中、跳过、反击、击毁及场景退出的真实顶层事务边界。
4. 找出武器 ID→动画 ID→组图/移动规律的完整索引关系，枚举当前 ROM 中实际使用的全部物理武器脚本和 opcode。
5. 建立机体→武器/动画→组图与公共特效的完整可达图，并盘点物理组图规律所在 8 位 ID 命名空间、共享指针和别名。
6. 建立 256 个 1 KiB CHR 页的四态所有权表：`occupied`、`reserved`、`allocatable`、`unproven`，记录静态引用、运行时映射、全零状态、相邻配对和证据来源。反向读者必须覆盖 `F2`、标题、地图、菜单、头像、变形/换装、剧情替换、双方机体、背景武器和公共特效；无法穷尽读者的页保持 `unproven`。全零只能作为线索。
7. 保存至少一组原始 Mesen 日志和截图，覆盖敌我双方、主动攻击、反击和大小型机体。

**输出**

- `output/mappings/` 下的战斗动画指针、CHR 页所有权和 RAM/Mapper 映射表。
- `output/reports/rom-build/fragment-weapon-unbind/<run-id>/` 下的 opcode 覆盖率与初始容量报告。
- `output/verification/fragment-weapon-chr/<run-id>/` 下的基线追踪日志和截图。
- 带稳定 case ID 的 `tests/emulator/fragment_weapon_cases.json` 语义清单 v1：在 Gate 0 冻结基线 profile/ROM 哈希、机体 ID、武器与动画 ID、敌我槽、攻击顺序、战斗结果、输入序列或状态文件哈希、最大帧数和关键帧。此时尚不能知道的编译布局、预期 CHR Bank 和候选 ROM 哈希必须显式写为 `pending`，不能预填猜测值。

**退出条件 / No-Go**

- 物理武器和碎片脚本的图块引用必须 100% 可枚举；发现未知间接引用则停止自动重映射方案。
- 双方 CHR 槽、基础 Bank 和共驻对象必须有一致的静态与动态证据；若考虑 C2，还必须解释所有恢复出口。
- 至少要证明一个目标碎片/武器 2 KiB 页可安全重排，或一个连续、偶数对齐的 2 KiB 页可安全分配给 PoC；只因全零不得通过。

### 阶段 1：只读 codec 与往返测试

**工作内容**

1. 为战斗外观记录建立有字段名但保留原始字节的 lossless 模型。
2. 为武器动画、物理组图规律、横纵移动规律和相关指针表建立边界明确的 codec。
3. 区分图块编号、坐标、属性/翻转位、重复/跳转和结束码；未知操作保持原字节并阻止需要重写的操作。
4. 对全部原始记录执行 decode→encode 往返，并验证指针范围、终止符和共享记录关系。

**退出条件 / No-Go**

- 未编辑的全部记录逐字节往返一致。
- 所有会被 packer 重写的图块操作数都有单元测试和至少一个 ROM 实例证据。
- 任一脚本越界、截断或存在未解析控制流时，不进入写入阶段。

### 阶段 2：离线静态链接器与容量决策

**工作内容**

1. 实现内存中的可达闭包、共驻约束图、跨页稳定武器槽位、确定性装箱、图块重映射和内容哈希去重，暂不写 ROM。
2. 用当前全部实际可达的机体和物理武器关系运行 C1 dry-run，输出闭包数量、每页图块、共享关系、冲突、去重率、重排页及所需新增 CHR 页。
3. 对至少一个共享武器、两个不同碎片页的静态布局做人工图块对照，证明共享脚本在两页使用相同本地图块号。
4. 将结果与阶段 0 的可重排/可分配 CHR 清单比较，保留安全余量并首先作出 C1 是否可交付的决策。
5. 仅对 C1 无解的真实组合估算 C2 稀疏组合页和 PRG 查询表，记录从 C1 升级的具体原因；若 C2 仍超限，再决定是否单独论证 D。
6. 在容量报告中冻结整数预算：`hardware_reserved_pairs`、`unproven_pairs`、`certified_relayout_pairs`、`certified_free_pairs`、`safety_reserve_pairs`、`required_total_pairs`、`required_c1_pairs`、可选的 `required_c2_pairs` 和 `max_supported_combinations`。`hardware_reserved_pairs` 与 `unproven_pairs` 永不进入可用分母；`safety_reserve_pairs` 是从已认证可重排/空闲集合中额外留出的余量。C1/C2 混用时 `required_total_pairs` 是最终总占用而非 C2 增量。在这些数值尚未确定前，容量 Gate 默认失败。
7. 确定性装箱完成后、任何 ROM 写入前，把布局 ID/哈希、各 case 的预期基础/运行/恢复 Bank 及可选 selector 写入用例清单 v2 并冻结；未进入 C2 时，全部 C2 case 和字段写为 `not_applicable` 并记录路线决策依据。

**退出条件 / No-Go**

- 同输入重复运行得到完全相同的页面、重映射表、顺序和哈希。
- 每个生成页重新解码后，碎片和武器引用均与源资产像素一致，共享武器在所有页的本地图块号满足全局脚本约束。
- 必须满足 `required_total_pairs <= certified_relayout_pairs + certified_free_pairs - safety_reserve_pairs`；`safety_reserve_pairs` 是报告中冻结的正整数，首版最低保留 1 个已认证页对，不得以“尚有一些余量”代替或降为 0。`hardware_reserved_pairs` 和 `unproven_pairs` 已在可用集合之外，不能再次扣除或误计为容量。若产品只支持有限组合，最大值必须等于报告中的 `max_supported_combinations`，由 UI 和构建器共同强制执行。
- 容量超限时只输出诊断，不得写半成品 ROM。
- C1 可装下时禁止为了“架构更灵活”直接加入运行时补丁；C1 无解时才进入 C2。
- 若 C2 目标组合也无法放入已证明可分配的 CHR，暂停并单独启动 CHR-RAM 研究，不继续产品化。

### 阶段 3：单机体、单武器静态链接 PoC

**工作内容**

1. 选择一个小型机体和一个 `42 69` 物理武器作为最小样本；再用敌方调用交叉验证同一静态页布局。
2. 把碎片与武器作为两项逻辑资产输入；链接器生成一个共驻 2 KiB 页、重写已确认的图块引用，并把偶数基页写入机体外观记录。不得安装运行时查询或切换补丁。
3. 记录 `$04D0/$04D1`、`$04D8/$04D9`、`$8000/$8001` 写入和 PPU 图块页，证明运行时仍是原装载时序，没有新增攻击期 Bank 切换。
4. 比较机体碎片像素、武器像素、动画时序、非目标页面和下一场战斗状态。
5. 候选 ROM 生成后，从构建报告读取实际 ROM SHA-256、IPS 基线身份和布局描述符哈希，写成用例清单 v3；先核对它们与候选文件逐字节匹配并锁定清单，再启动 Mesen，禁止以测试后的观察值回填期望。

**退出条件 / No-Go**

- 我方主动攻击、敌方主动攻击、反击和场景退出均无碎片花图；整个场景使用静态生成页，不依赖攻击结束恢复。
- 关闭功能开关后的构建与旧构建逐字节一致。
- 出现未解释的额外 Mapper 写入、共享脚本错图或非目标 CHR 差异时停止，不进入通用化。

### 阶段 4A：静态链接器产品化与构建集成

**工作内容**

1. 对全部实际可达闭包执行全局装箱，处理共享武器的固定本地图块号、共享动画、别名和内容去重。
2. 将静态生成页、重写脚本和机体外观 Bank 记录纳入正式构建器，增加 Bank/指针/边界/保护区断言。
3. 在构建报告中记录每个运行页的闭包、来源、页号、图块数、重映射、哈希、共享武器槽位和引用者。
4. 只有项目实际使用独立资产时才重排或分配相关资源；不安装运行时 Hook。

**退出条件 / No-Go**

- 自动测试、原装载路径的 Py65 测试和最小 Mesen 验证矩阵全部通过。
- 未修改区域、受保护 Bank 和无关 CHR 页的哈希符合白名单差异。
- 全部目标闭包可装入且保留明确安全余量；否则不开放 GUI，转入阶段 4B 论证。

### 阶段 4B：条件式攻击期组合页

只有阶段 4A 证明固定共驻页确实不足时才执行；若 4A 已满足目标，本阶段永久跳过。

**工作内容**

1. 只为实际可达的 `(battle_appearance_id/unit_id, physical_animation_id)` 生成稀疏表项 `{chr_pair, optional_fragment_script_selector, optional_weapon_animation_or_composition_selector}`，不生成完整笛卡尔积；敌我 side 仅参与目标 shadow 槽选择。
2. 先完成 RAM/零页所有权审计，为保存 Bank、active-state 或引用计数认证明确地址；证明其不与主逻辑、NMI、IRQ、音频、存档或已有扩展状态冲突。若无安全状态存储，本阶段直接 No-Go。
3. 选择最小 Hook，使当前机体/动画在首次解析任何依赖表项的脚本或图块前切到组合页并选择可选脚本 selector；保护 A/X/Y、状态寄存器、栈、零页、PRG Bank 和 MMC3 模式影子现场。
4. 保持基础碎片和公共资源的本地图块布局；若武器或碎片需要不同本地编号，表项必须同时选择对应脚本副本，并验证指针/ID 命名空间容量。
5. 实现幂等切换、顶层攻击事务状态、必要的 active-state/引用计数、可靠恢复和场景退出兜底；验证连续攻击、并发对象、反击、未命中、击毁和提前结束。
6. 优先把查询与执行代码放入托管 PRG；若必须修改固定 Bank，建立新 ROM profile 和精确签名。

**退出条件 / No-Go**

- 运行时查表、切换和恢复的 Py65 测试及完整 Mesen 矩阵全部通过。
- 攻击方切页不得覆盖防守方精灵窗口，CHR shadow 与真实 Mapper 状态始终一致。
- NMI/IRQ 抢占、嵌套/并发对象和所有退出路径中，寄存器、栈深、PRG Bank、MMC3 D7 模式影子及 RAM canary 均保持预期；找不到可认证 RAM 即为硬 No-Go。
- 运行时表或补丁不能在现有保护规则下被精确描述时，不得放宽为“允许任意差异”。
- 任一提前退出或并发对象生命周期不能证明可恢复时为运行时硬 No-Go，停止 C2；CHR-RAM 不能解决这个生命周期错误。
- 只有 C2 的 CHR-ROM 容量门失败时，下一步才可另立 CHR-RAM 研究方案。

### 阶段 5：修改器与工程格式接入

**工作内容**

1. 接入独立资产模型、绑定操作、组合预览、容量诊断和保存前阻断。
2. 完成 `.dcmod` 保存/载入、迁移、撤销/重做和异常输入处理。
3. 扩展 `.dcunit` 清单和依赖冲突流程；保持旧版本包可读，或给出明确的不兼容信息。
4. 写入并读取已编译布局描述符；验证匹配 `.dcmod` 可继续编辑，而单独重开派生 ROM 时新语义控件只读、普通字段能力不退化、无修改另存字节不变。
5. 只在底层写入验证全部通过后开放机体碎片和物理武器相关控件。
6. 汇总确认 `docs/DC修改器使用说明.md` 已随每项实际编辑器变更同步界面、操作、校验、限制和截图；遗漏项必须在本阶段补齐，但不能把前述同步义务推迟到这里。

**退出条件 / No-Go**

- UI 不允许构造构建器无法表达的状态。
- 保存再加载、撤销再重做、导出再导入均保持资产哈希和绑定关系。
- 老工程不启用新功能时行为及构建结果不变。
- 单向 schema 迁移不覆盖原工程；派生 ROM 单独重开的只读语义和匹配工程重开的可编辑语义都有自动测试。

### 阶段 6：全量验证、交付与交接

**工作内容**

1. 只有阶段 0—5 的 Gate 已通过，才在隔离路径分别生成“功能关闭基线候选”和“固定验收工程生成的功能开启候选”；此时仍不得覆盖任何正式产物。
2. 对两个候选运行全部 `unittest`、ROM/IPS 等价、差异白名单和 Mesen 矩阵，记录容量、性能、兼容性及未覆盖边界。
3. 用功能候选和匹配工程生成候选 GUI 截图，完成人工/像素视觉审查，再从同一候选文档树生成 PDF 和候选 EXE，执行工程载入、保存、容量阻断及只读派生 ROM 自检。
4. 汇总确认 `docs/交接文档.md` 已随实际 ROM/CHR/运行时变更同步布局、补丁点和阶段验证结论，并补入最终哈希；不得改写 `docs/提交记录.md` 的既有历史条目，实际实现完成后可按项目惯例追加新记录。
5. 生成并交叉校验 ROM、IPS、匹配 `.dcmod`、容量报告、映射表、验证日志和候选 SHA-256 清单。全部通过后，才由事务式晋升包装器发布获准产物；文件清单更新和交接包验证是该事务的最后两步，任一步失败都恢复晋升前快照。

**退出条件**

- 第 11 节完成定义全部满足，且没有被降级为普通警告的 No-Go 项。
- 每个失败注入点均证明现有正式 ROM、IPS、PDF、EXE、报告、截图和文件清单哈希不变；只有完整 Gate 6 成功路径能够晋升。

静态 C1 路线的 Py65 或等价 6502 级测试至少要证明：

1. 战斗外观 offset `+7` 的偶数基页经原装载路径进入正确的 `$04D0/$04D1` 和 CHR 影子槽。
2. 我方、敌方、`42`、`C2` 的高低半区语义保持不变。
3. 静态生成页不会引入攻击开始/结束时的额外 Mapper 切换。
4. “继承”模式完全保持原记录和原路径。

1. 查询表输入相同则得到相同 `{chr_pair, optional_fragment_script_selector, optional_weapon_animation_or_composition_selector}`，VM 实际从返回的 selector 解析对应脚本。
2. 我方和敌方只写正确的 CHR 影子槽，不触碰其他四个 CHR 寄存器影子。
3. 切换值被 MMC3 提交例程按预期写出。
4. 恢复使用实际保存值而非硬编码假定值。
5. 无绑定或表项非法时保持原行为，不执行越界 Bank 写入。

### 7.2 构建与静态断言

每次 PoC、候选及正式构建都必须自动验证：

- 输入 ROM 身份、Mapper、PRG/CHR 大小和有效 CHR 文件区间。
- 相对当前 464 KiB 推荐基线的 C1/C2 功能差异不得修改 16 字节 iNES 头；Mapper、PRG 和 CHR 容量均保持不变，任一头部差异都是 No-Go。完整构建从只读源生成 464 KiB 基线时原有头部扩容仍按现行构建规则验证，不能与功能差异混为一谈。
- 每个指针表、脚本范围、终止符、Bank 编码及固定/可切 Bank 假设。
- 静态运行页或 C2 组合页均为 2 KiB 偶数对齐，且图块计数、引用闭包、共享武器槽位、所有权、内容哈希和相互不重叠。
- C1 的重写脚本和机体外观记录只落入声明区间；若使用 C2，PRG 查询表及补丁不得覆盖 `$61-$64` 音频区、其他托管资源或未经声明的固定 Bank 字节。
- 只有声明的 CHR 页发生变化；每个变化页都有对应静态布局或 C2 组合记录。
- 每个变化页的全局反向引用闭包均已枚举；所有旧读者要么被重定向，要么其所读位置内容逐字节保持不变。标题、地图、菜单、头像、变形/剧情替换、背景武器和公共特效均有对应回归证据。
- 构建失败不留下被当作正式结果的 ROM、IPS 或工程副本。
- 每个 C2 Hook 必须记录精确文件 offset、长度、preimage、postimage 和所属 profile；应用前逐字节核对 preimage，不得只把整个 PRG Bank 加入宽泛白名单。
- 每个 IPS/ROM 报告必须固定 `basePath`、`baseSize` 和 `baseSha256`。完整构建的只读源应记录 `786448` 字节及 SHA-256 `267CFA5E6273E0FE3557D5339B0E50172BCF25475283944C7E8372276FB3493C`；以当前推荐 464 KiB 基线为功能差异基准时，应记录 `1310736` 字节及 SHA-256 `82C218275459D53C0F306F6BC036C4797316976E0FA7AD1D5A8247E338995B8E`。IPS 应用于报告声明的唯一基线后与派生 ROM 逐字节一致。
- 相同输入两次构建的 ROM、IPS、映射表和报告哈希一致。

- `tests/emulator/fragment_weapon_cases.json`：机器可读的稳定用例清单。
- `tools/run_fragment_weapon_mesen_validation.ps1`：复制 ROM、Lua、状态/输入、锁定的 Mesen 设置到纯 ASCII 临时目录，核对复制前后哈希，运行 `--testrunner`，收集日志/截图并返回测试退出码。

Lua 必须为每例输出唯一 `CASE <id> PASS/FAIL`，总结果用 `emu.stop(0)` / `emu.stop(1)` 结束；超时、复位、死循环、缺日志或缺截图均为失败。包装器生成 `results.json`，把 case ID、profile/ROM 哈希、状态或输入哈希、设置哈希、期望值、实际值、日志、截图和 PASS/FAIL 关联起来。`results.json` 必须逐项列出下表的全部适用 ID；条件 C2 未进入时也要逐项记录 `NOT_APPLICABLE` 和 Gate 决策报告，不能简单漏项。

不能只验证“一次我方攻击”。用例清单采用三次只前进、不回填的冻结协议：

1. **Gate 0 / v1（语义冻结）**：在任何 ROM 写入前固定基线 profile/ROM 哈希、具体机体、武器/动画、敌我槽、输入/状态哈希、结果分支、最大帧数和关键帧；编译后字段保持 `pending`。
2. **阶段 2 / v2（布局冻结）**：确定性装箱完成后、ROM 写入前固定布局 ID/哈希、预期基础/运行/恢复 Bank 和可选 selector；未进入 C2 时其用例/字段固定为 `not_applicable`。
3. **阶段 3 或 6 / v3（候选身份冻结）**：候选生成后，从构建报告写入候选 ROM/IPS/工程 SHA-256 和 ROM 内描述符哈希，核对文件后锁定清单，随后才运行 Mesen。

每次冻结都保存版本号、前版哈希、操作者/工具版本和批准记录。Mesen 只接受锁定的 v3；若装箱或候选变化，必须从受影响阶段产生新版本并重新审批，禁止用测试观察值原地修改期望。若一个样本不能覆盖下列表述的两个分支，应拆成带后缀的独立 case。

1. 基线 ROM 与派生 ROM 使用同一状态/输入回放、同一已哈希的 Mesen 设置和同一关键帧编号。

## 8. 风险、失败判据和缓解

| 风险 | 后果 | 缓解与失败判据 |
|---|---|---|
| 把全零 CHR 页误判为空闲 | 清屏、转场或特定单位花图 | 必须同时有静态引用扫描和 Mesen 运行追踪；无所有权证据即不可分配 |
| 图块引用未被完整解析 | 重映射后个别帧取错图 | opcode 和引用覆盖率必须 100%；未知间接引用是 No-Go，不做启发式改写 |
| 单机体共驻闭包超过可用槽 | C1 无法保持原运行机制 | 报出具体碎片、武器和超额图块；评估安全脚本复制，仍无解才进入 C2 |
| 共享武器在不同页需要不同本地图块号 | 一份全局组图脚本不能同时正确 | 链接器把跨页稳定槽位作为硬约束；无法满足时确定性失败，不原地破坏共享脚本 |
| C2 组合数爆炸 | 256 KiB CHR 不足 | 仅生成实际可达稀疏组合并按内容去重；构建前全量 dry-run；容量不足转入 CHR-RAM 论证 |
| 敌我、42/C2 或高低半区判断错误 | 只在敌方/反击时花图 | 槽位相关矩阵全覆盖，追踪 `$8000/$8001` 和 PPU 页，不只看静态截图 |
| C2 恢复遗漏 | 下一段动画或下一场战斗花图 | C1 不需要恢复；C2 的正常、异常和场景退出均恢复，并用连续两场测试验证 |
| C2 状态 RAM 或中断重入冲突 | 随机花图、音频损坏、死机或栈失衡 | 先认证 RAM 所有权；用 canary、NMI/IRQ 抢占、嵌套对象、寄存器和栈平衡测试；无安全地址即 No-Go |
| 大型机或头像争用 PPU 槽 | 特定组合损坏 | 阶段 0 枚举所有战斗布局；没有“独立空槽”证据就不采用方案 B |
| 固定 Bank 补丁破坏既有系统 | 音频、事件或通用 VM 回归 | 优先普通 PRG Bank；必须改固定 Bank 时使用最小白名单差异并更新保护断言 |
| 项目/机体包共享资产冲突 | 导入后隐式改变其他机体 | 内容哈希、显式依赖和冲突选择；事务化导入及撤销 |
| 模拟器掩盖精灵限制 | 在手机、其他模拟器或实机闪烁 | Mesen 不开启解除 8 精灵限制作为正式验收；记录 OAM 与 overflow，不宣称突破硬件限制 |
| Mapper 194 实机差异 | 模拟器通过但烧录卡失败 | 继续记录实机未验证边界；如面向实机，另做目标烧录卡验证 |

以下任一情况发生即暂停实现，不得用扩大写入白名单、忽略测试或隐藏警告的方式继续：

- 无法证明当前动画使用的全部图块引用可安全重写。
- 无法证明 PoC 目标页可安全重排/分配，或静态闭包和 C2 组合容量均超过已验证空间。
- 若采用 C2，任一敌我/反击/退出路径不能稳定恢复原 Bank。
- 必须改变 Mapper 才能达到第一版目标。
- 未启用功能的基线构建出现无法解释的字节差异。
- 出现无法归类的固定 Bank、CHR 或音频区域变化。

## 9. 回退方案

1. 功能以工程级 feature flag 和“继承机体碎片图库”默认模式保护；未使用时不安装新资源或补丁。
2. 所有实验只生成第 6 节列出的 `experiments` / `<run-id>` 路径，不修改 `references/`，也不更新正式文件清单。
3. PoC 失败时删除的是派生构建步骤和明确的实验输出，不回滚用户其他工作，也不使用破坏性 Git 操作。
4. C1 无解时，保留 codec、所有权表和 dry-run 报告作为 C2 输入；C2 容量不足时再作为 D 的输入。不发布只能支持部分组合却没有容量提示的版本。
5. 若静态链接或条件式运行时通用化失败，修改器继续保持相关控件只读，当前稳定构建链和使用说明不宣称支持该功能。
6. `.dcmod` schema 迁移失败或回退时使用迁移前原文件/恢复副本，绝不拿单向迁移结果覆盖唯一工程源。
7. 回退完成的机器判据是：`output/rom/DC_kuorong_464K.nes` 恢复为 SHA-256 `82C218275459D53C0F306F6BC036C4797316976E0FA7AD1D5A8247E338995B8E`，完整 `unittest` 通过，现有 Mesen 冒烟 17/17 且退出码 0，第 675 帧标题截图仍为 `B315051DA2C1CF8CD0AF743879F52CB5D95E54AF07EA5921600312A423D936A3`，随后再验证正式清单。

## 11. 完成定义

只有同时满足以下条件，才可把功能标记为“已实现”：

- 用户可以分别管理机体碎片和物理武器资产，并在两个碎片页不同的机体间复用同一武器资产。
- 构建器优先自动生成、重映射、去重和分配静态共驻页；只有 C1 无解时才使用经过完整验证的 C2 组合页。容量不足或引用未知时在输出前明确失败。
- 容量报告分别冻结硬件保留/未证明、已认证可重排/空闲、额外安全余量、C1/C2 总占用和最大支持组合数，满足第 6 节的数值不等式，UI 与构建器执行相同上限。
- 未启用独立资产时，构建输出与实现前基线逐字节一致。
- 全部 codec 对原数据 lossless 往返，完整自动测试通过。
- Mesen 敌我、主动/反击、大小型、42/C2、命中/未命中、击毁和连续战斗矩阵通过。
- `results.json` 对第 7.3 节每个稳定 case ID、每个新功能可写 profile 都有 `PASS`，或仅对未进入的条件 C2 case 给出可追溯的 `NOT_APPLICABLE`；没有缺失、重复或未知 case。
- C1 运行时无新增切换；若采用 C2，切换期间机体碎片、头像和背景无非预期变化，所有出口恢复原 CHR Bank。
- ROM/IPS 等价、变化 Bank/CHR 白名单、容量报告、映射表、截图和日志齐全。
- 每个变化 CHR 页的全局旧读者都已重定向或证明内容不变，非战斗标题、地图、菜单、头像、变形/剧情替换、背景武器和公共特效回归通过。
- 修改器使用说明、交接文档、界面截图、构建产物和文件清单已同步。
- `.dcmod` 可无损续编且迁移不覆盖旧工程；候选及获准发布工程的 SHA-256、布局/资产哈希与 ROM 描述符和验证结果完全匹配；派生 ROM 单独重开时按约定只读展示已编译布局，无修改另存字节不变。
- 现有 Mesen 冒烟 17/17、退出码 0，第 675 帧标题截图哈希保持 `B315051DA2C1CF8CD0AF743879F52CB5D95E54AF07EA5921600312A423D936A3`。
- 上述自动、构建和 Mesen 验收对 Gate 0 声明的每一个“新功能可写 profile”分别通过；未认证旧 ROM 只保持既有可读能力，不列为已支持写入。
- 未解决的 NES 精灵上限、模拟器兼容性和实机边界被准确记录，没有宣传为已消除。

## 12. 执行前仍需关闭的决策

1. 当前战斗外观 10 字节记录每一字段的最终语义，尤其是双方碎片 Bank 的来源和保存位置。
2. 物理武器的稳定主键应使用武器 ID、动画 ID、组图规律 ID，还是三者组合。
3. `42 69` / `C2 69` 全部控制流及图块引用是否能 100% 静态枚举。
4. 当前 256 KiB CHR 中哪些相邻 2 KiB 页可由静态和动态证据证明可重排或可分配。
5. 每机体完整可达闭包、共享武器固定本地槽约束、去重率和安全余量是否允许 C1 产品化。
6. 若 C1 无解，预计 C2 稀疏组合数是否可容纳，以及最小运行时挂钩能否避免修改受保护的固定 Bank。
7. 若采用 C2，所有提前结束和场景退出路径中，哪个位置适合作为最终兜底恢复点。
8. `.dcmod` 和 `.dcunit` 是否需要版本升级，以及共享资产冲突的最终用户流程。
9. 第一版是否只承诺推荐 464 KiB 基线，还是同时支持旧 200 KiB 兼容基线；不得在未验证时默认两者布局相同。

这些决策应在各自对应阶段的出口关闭：第 1—4 项主要属于阶段 0—2，第 5 项在阶段 2/4A 关闭，第 6—7 项仅在进入阶段 4B 时关闭，第 8 项在阶段 5 关闭，第 9 项必须在首次写入对应基线前关闭。条件路线未进入时，应把对应决策明确标记为“不适用”，而不是伪装成已验证。阶段 0 只需关闭其自身退出条件后即可进入只读 codec 和 dry-run；任何 ROM 写入仍须等相应写入阶段的入口条件满足。本文本身不关闭这些决策，也不授权修改 ROM。
