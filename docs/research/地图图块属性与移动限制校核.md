# 地图图块属性、颜色表与移动限制运行时校核

## 结论

此前实现把每段开头四字节误当成同段图块属性的头部，导致图库 B—H 的图形与后一组属性数组错配。运行时实际以“80 字节图块数组＋4 字节本图库颜色/图形编号”为一条逻辑记录。修正后，用户截图中的图库 D 位图5与旧工具完全一致：颜色表2、防御85%、非海、空中可通行、陆补正2格、海上不补正。

## 运行时证据

Mesen 只读跟踪第一关加载过程得到：

- CPU `$8237` 从当前记录指针 `+0x10` 连续读取16个防御/海属性字节并写入 RAM `$750F—$751E`；
- CPU `$832B` 从指针 `+0x00` 读取16个颜色表字节并写入 RAM `$06C0—$06CF`；原码 `$00/$55/$AA/$FF` 是四个2位调色板编号重复填充后的 PPU 属性字节，对应颜色表0/1/2/3；
- CPU `$8563` 从指针 `+0x50` 读取颜色表1的三个 NES 色号，再从 `+0x53` 读取图库编号；
- 第一关图库 D 的运行时指针为 CPU `$A0FC`，对应 PRG 偏移 `$60FC`、文件偏移 `0x610C`。该地址正是原先被错误归给图库 C 的16项数组；D 的颜色和图库编号则位于同一逻辑记录末尾 `0x615C—0x615F`；
- 指针表实际包含 A—H 八个记录起点 `$A000/$A054/$A0A8/$A0FC/$A150/$A1A4/$A1F8/$A24C`，因此图库 H 不是无记录，只是此前遗漏；
- 战斗代码读取 RAM `$750F,Y` 后以 `BMI` 检查 bit7，并在防御计算前执行 `AND #$7F`。这证明最高位是独立海属性标志，低7位才是防御百分比。

跟踪脚本为 `tools/research/emulator/dc_tile_attribute_runtime_probe.lua`，本轮输出归档在 `output/build/legacy-diff-audit/mesen-palette-probe-6-baseline/tile-attribute-runtime-stdout.txt`。

## 正确字段布局

A—H 的逻辑记录从文件偏移 `0x6010` 起，每条84字节：

| 相对偏移 | 长度 | 含义 | 合法值 |
|---|---:|---|---|
| `+0` | 16 | 各位图颜色表 | `$00/$55/$AA/$FF` → 表0/1/2/3 |
| `+16` | 16 | 防御值低7位＋海属性 bit7 | 低7位 `0—127`，bit7 二值 |
| `+32` | 16 | 空中通行 | `$00` 不能、`$01` 可以 |
| `+48` | 16 | 陆地移动 | `$00` 不能、`$01` 不补正、`$02—$10` 补正1—15格 |
| `+64` | 16 | 海上移动 | 同上 |
| `+80` | 3 | 颜色表1的三个 NES 色号 | `$00—$3F` |
| `+83` | 1 | 图形选择器（只读身份） | A—H 固定值 |

源 ROM、扩容基线和推荐 ROM 的完整 A—H 逻辑记录区 SHA-256 均为 `1AEC616564157FEE076B295A51AD4ACB895C9905B3CED4ECDB232AF8BF1FF931`。

## 截图样本：图库 D 位图5

图库 D 逻辑记录从 `0x610C` 开始。位图5原码为：颜色 `$AA`、防御/海 `$55`、空中 `$01`、陆地 `$03`、海上 `$01`，所以解码结果为：

- 颜色表2；
- 防御补正85%，海属性否；
- 空中可以通行；
- 陆地补正2格；
- 海上不补正。

这五项与用户提供的旧工具截图逐项一致。原先新工具显示的100%等值来自错读下一段 D 数组，现已纠正。

## 海属性总表

按运行时实际记录读取，海属性为“是”的只有图库 A 位图5和图库 B 位图5；图库 C—H 均没有置 bit7 的图块。工具不再按画面推断，也不自动补写。若用户主动勾选或取消，只改同一防御字节的 bit7，低7位防御值保持不变。

## 回归门禁

- A—H 完整记录区必须匹配上述 SHA-256；
- 八个运行时颜色表数组必须与预览路由逐项一致；
- D5 必须解码为 `(表2, 85, 非海, 空1, 陆3, 海1)`；
- 海属性索引必须为 `A:[5]、B:[5]、C—H:[]`；
- 空中字段出现 `$02` 及以上时 Codec 必须拒绝编辑；
- 图库 H 必须可编辑，图形选择器 `$45` 保持只读；
- 修改颜色、防御或移动字段不得产生海属性旁写。
