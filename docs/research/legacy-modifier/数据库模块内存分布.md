# 数据库六模块 ROM 内存分布

## 结论

数据库窗口不是一块可以跨模块借用的连续空间。当前支持 ROM 中，六个主模块由固定指针表、固定记录、可重排共享池和少量离散运行时代码操作数组成。界面“数据库 → 内存分布…”按当前内存草稿实时重算，不把 `00`、`FF`、重复指针或旧工具曾经写过的差分包络误认为空闲区。

以当前 `output/rom/DC_kuorong_464K.nes` 为基准，共识别 34 个数据区：12 个有严格边界和重排器的独立/共享池合计 `19,618 B`，当前使用 `19,369 B`，安全剩余 `249 B`；其余固定区合计展示 `8,086 B`，但不提供增长容量。当前唯一有剩余的数据库共享池是系统文字池，剩余 `249 B`。这些字节只能供系统文字内部重排，不能借给人物、武器、战斗对话或道具。

## 固定区

- 机体修改：机体属性指针表、16 字节物理属性记录、名称指针表、两槽武器配置表。旧/当前 ROM 中重复属性指针仅作为输入压缩格式读取；首次修改目标 ID 时自动建立独立属性镜像并展开为 255 条记录，不再作为联动修改关系。
- 人物修改：普通/战斗名称指针表、属性指针表、头像指针表、精神消耗表、台词绑定指针表。
- 武器修改：武器属性指针表、6 字节物理属性记录、名称指针表。
- 其他修改1：成长方式指针表、50 字节成长记录、99 项累计经验、4×16 距离命中补正、6 组初始人物/机体，以及双击/伤害/命中/道具效果的离散操作数。
- 其他修改2：道具名称指针表、24 项价格、5 个固定长度商店记录。

固定区显示“已用＝容量、可改值”。这不表示字段不可编辑，也不表示每个字节都必然非零，而是没有证据允许改变区域长度或占用相邻字节。重复指针只表示多个逻辑编号共用同一物理记录，不能把未被某个逻辑编号单独占用的地址当作新增容量。

上表的机体名称按旧版编辑语义先把当前 255 个逻辑 ID 展开为独立记录，因此基线占用为 `1456 B`，并在此基础上严格保留旧修改器实证得到的 `6701 B` 净增长余量，总门禁为 `8157 B`。这不是把当前 ROM 的 693 B 原生物理区谎报成 8157 B：未修改时不写扩展区；原生区确实放不下时，才通过已验证的资源选择器 `$13` 安装一组 16 KiB Bank pair，且名称写入器只开放上述 8157 B 逻辑容量，余下物理字节不冒充旧版可用量。活动指针表位于 CPU `$8010`，编辑器规范指针表位于 `$8210`，名称正文从 `$8410` 起。两张表分别保证游戏运行时读取和工程重开后的逻辑 ID 身份；容量值写入 `DCUNAME2` 头并随 ROM 重开恢复。当前推荐 ROM 若有重复名称指针，直接改名只拆分正在修改的逻辑 ID；这属于对当前 ROM 布局的兼容处理，并非旧修改器的“共用名称”规则。

## 动态计算与门禁

界面每次打开或点击“重新读取当前草稿”都会从 `RomProject.working` 读取实时指针、唯一物理记录、结束码和已验证池尾。总览只对唯一 `pool_key` 求和，因此普通/战斗人物名称这类多入口共享池不会被重复统计。任何写入、撤销、重做或窗口草稿提交后均可重新测量。

旧修改器全模块保存差分继续保留在 `旧修改器全模块内存分布.md` 和 `output/verification/legacy-memory-distribution.json`；它们证明旧工具写过哪些区域，但不直接证明容量。本页的“剩余”只来自当前产品已有的边界验证和整池重排器。

旧版冷启动样本已证明，人物属性和人物台词也必须像机体属性一样按逻辑 ID 自动拆分；用户进一步确认头像配置同样不存在用户层共用规则。头像与机体战斗外观尾区已按 7 B、9/10 B 记录实现逐字节零差异重建，当前动态余量为 798 B；头像配置修改自动拆分目标人物，CHR 图块的物理复用则继续作为另一类影响单独提示。详细证据见《人物修改分配规则复核-2026-09-28.md》。
